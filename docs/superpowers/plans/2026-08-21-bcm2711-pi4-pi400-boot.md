# BCM2711 Pi 4/Pi 400 Boot Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the `rpi4_defconfig` image boot through the MMU handoff and deliver its 200 Hz tick through BCM2711's GICv2 on Raspberry Pi 4 and Pi 400 hardware.

**Architecture:** Keep the pre-C BCM2711 mailbox address selection in the shared Raspberry Pi startup assembly. Keep the Pi 4 GICv2 and generic-timer implementation in Raspberry Pi machine files, modelled on but not shared with `virt-arm`; Pi 1-3 retain `raspi_int.c`'s legacy/local interrupt controller path. Make cache operation names distinguish invalidation from clean-and-invalidate so the MMU handoff cannot lose descriptors.

**Tech Stack:** C90 with GNU extensions, ARMv7/AArch32 assembly, ARM GICv2, ARM generic physical timer, GNU Make, `arm-none-eabi-gcc`.

## Global Constraints

- Preserve Pi 1-3 startup, legacy interrupt-controller, and local-timer behaviour.
- Select the secondary-core mailbox address before C code, because `raspi_board` is not initialized until `raspi_vcmem_init()`.
- Keep BCM2711 GICv2 addresses and interrupt policy under `bios/machine/raspi/` or Raspberry Pi BIOS files.
- Do not refactor the `virt-arm` GICv2 driver into a shared abstraction in this issue.
- Do not change PCIe, xHCI, framebuffer-mode, or Pixel Valve VBL code.
- Build all changed ARM configurations with `gmake`; real Pi 4/Pi 400 testing is required because QEMU does not validate BCM2711's physical interrupt path.

- [ ] **Step 2: Run the extended contract test to verify it fails**

- [ ] **Step 3: Implement the Pi 4-only GICv2 driver**

Create `raspi_gic.c` from the proven protocol in `virt_pic.c`, but use BCM2711 constants:

```c
#define RASPI_GIC_DIST_BASE 0xff841000UL
#define RASPI_GIC_CPU_BASE  0xff842000UL
#define RASPI_GIC_SPURIOUS  1023UL
```

Initialize the handler table to zero, disable all implemented interrupt-enable words, enable the distributor, set `GICC_PMR` to `0xff`, and enable the CPU interface. `raspi_gic_connect_irq()` assigns priority `0x80`, targets only SPIs (`irq >= 32`) at CPU 0, and sets/clears `GICD_ISENABLER`/`GICD_ICENABLER` when registering/unregistering. The dispatcher reads IAR, returns for 1023 without EOI, invokes a registered handler, and writes the original IAR to EOIR.

Declare exactly these functions in `raspi_gic.h`, guarded by `TARGET_RPI4`.

In `raspi_int.c`, branch `raspi_interrupt_init()`, `raspi_connect_irq()`, and `raspi_int_handler()` to the GIC functions for `TARGET_RPI4`; leave existing code compiled for Pi 1-3. Add `raspi_gic.o` to `obj-$(TARGET_RPI4)`.

Run: `sh tools/test-rpi4-boot-contract.sh`

Expected: non-zero exit because the current generic timer registers through `raspi_connect_irq()` and expects ARM-local pending bits.

- [ ] **Step 3: Implement Pi 4 timer programming and tick rescheduling**

For `TARGET_RPI4`, read `CNTFRQ`, calculate `ticks_per_hz = CNTFRQ / 200`, register `raspi_timer3_handler` on PPI 30, program the initial `CNTP_CVAL`, set `CNTP_CTL` enable bit, and execute an ISB. In the timer handler, update `CNTP_CVAL` by `ticks_per_hz` after calling `vector_5ms()` and serial polling. Do not read the obsolete BCM2711 ARM-local prescaler or local pending register.

Keep the existing system-timer logic byte-for-byte equivalent in the non-Pi-4 compile path.
Keep `raspi_board_t` unchanged in this issue: its generic-timer fields remain
part of the Pi 2/Pi 3 board description even though the new Pi 4 path obtains
the counter frequency directly from `CNTFRQ`.
