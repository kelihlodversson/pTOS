Process entry contract
======================

This document defines the register and stack state at the first instruction
of a loaded user process.  It applies to the ARM, x32 and m68k ports. It is not
the syscall ABI; the x32 syscall ABI is a separate contract.

The launcher selects the role. The standard ELF and native basepage
conventions communicate it explicitly. The classic m68k basepage convention
encodes it in the entry registers and stack.

The standard ELF initial stack (doc/elf-shared.txt) is used for PT_INTERP
and for static ELF loaded with kernel-owned launch vectors. The initial
stack pointer is 16-byte aligned and points to argc, followed by 32-bit
argv, envp and auxv. AT_PTOS_BASEPAGE locates the program's basepage.
Static vector entry goes directly to AT_ENTRY with AT_BASE zero. The
dynamic interpreter transfers to AT_ENTRY with a finalizer callback for
the application CRT. The callback is in D1 on m68k, R0 on ARM, and RDX on
x32. Static entry sets it to zero.

AT_PTOS_ENTRY_TYPE (0x5006) is an ELF32 auxiliary-vector word. A value of
zero selects program startup. A value of one selects accessory startup.
An absent tag also selects program startup. The current kernel emits the
tag for accessory launches. ELF CRTs
set the GEM _app variable before application preinitializers and enter the
same main(argc, argv, envp) in either role. Link the CRT first in the
executable so its preinitializer precedes the application's. The stack
and finalizer contract is identical for both roles.

Pexecve starts an ordinary program. A PROCESS_EXEC_PREPARE or
PROCESS_EXEC_START request can combine PROCESS_EXEC_ACCESSORY with
PROCESS_EXEC_VECTOR_ARGS for an independent ELF accessory. The external
desktop requests this role with shel_write(SWM_LAUNCHACC, ...). libaes
passes the flag through the PROCESS request and takes its own AES
classification from the runtime launch role, independently of the
executable's name. The role describes startup and grants no permission
to the launched process.

The external desktop and libaes use the same role values on every port.
The runtime supplies the private __ptos_entry_type() accessor before
application startup. lib/entry_role.h defines this interface. The standard
libcmini ELF and x32 libptos runtimes obtain the role from auxv. A classic
PRG runtime can obtain it from the program or accessory basepage entry
convention when adapted for libaes. A port must also provide a launch
backend that admits the requested format and role. The external desktop
currently uses the x32 ELF PROCESS backend. ARM and m68k kernel AES use
the staged launch described below. External libaes ports on ARM, m68k
and ColdFire remain future work.

The shared-address-space ARM and m68k kernel AES loaders also start
standard ELF accessories. The executable's PT_NOTE identifies the
standard CRT through the note name "pTOS" (with its NUL), type
0x50544f53 and a 32-bit descriptor value of one, all in target byte order.
The note describes the supported entry convention. Kernel AES supplies
the accessory role and a stack containing the executable pathname as
argv[0] and an empty environment. Marked m68k ELF programs also receive
standard entry when started as applications with classic Pexec(0). Existing
unmarked staged images use basepage entry, and classic PRGs retain their
original startup.

    ENTRY_PROGRAM = 0
    ENTRY_ACCESSORY = 1

Basepage entry
--------------

libcmini startup records the supplied basepage, selects the startup routine
from the explicit type, and establishes the C-call stack convention. The
x32 external desktop launches accessories through the standard ELF PROCESS
path above. Its legacy basepage convention is shown for program entry.

| Target | Launch | Producer | Consumer | Basepage | Type | User stack at process entry | Privilege | Termination |
|--------|--------|----------|----------|----------|------|-----------------------------|-----------|-------------|
| ARM | program | proc_go() | libcmini _crtinit() | r0 | r1 = ENTRY_PROGRAM | SP at p_hitpa, 8-byte aligned | user | Pterm returns through GEMDOS to the parent launch path |
| ARM | accessory | AES gotopgm() | libcmini _acc_main() | r0 | r1 = ENTRY_ACCESSORY | SP at p_hitpa, 8-byte aligned | user | Pterm returns through the AES accessory lifecycle |
| x32 | program | x32 process launcher | libcmini _crtinit() | RDI | RSI = ENTRY_PROGRAM | RSP + 8 divisible by 16 at process entry; libcmini preserves RSP when tail-jumping to C | ring 3 | Pterm resumes the saved launching kernel context |

The x32 ring-3 transition must write RDI and RSI explicitly immediately
before iretq.  At process entry, the x32 launcher must provide an RSP for which
RSP + 8 is divisible by 16.  libcmini must preserve RSP when tail-jumping into
C, so the C function-entry rule remains RSP + 8 divisible by 16.

The ARM launchers likewise initialize r0, r1, and the aligned stack before
entering user code.  libcmini must not infer the launch type from p_parent,
the filename, or an unspecified register value.

m68k
----

With basepage entry an ordinary program receives its basepage at 4(sp),
with A0 cleared. gotopgm()
supplies a desk accessory's basepage in A0.  No entry-type register is added
to the m68k ABI; startup code must use the launch convention selected by the
existing launcher.

Verification
------------

Each target must provide a small ordinary-program and accessory probe.  The
probe records the basepage register, the explicit type, and the entry stack
alignment before making GEMDOS or AES calls.  A successful image build alone
does not verify this contract.
