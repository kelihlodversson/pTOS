Historical Pexec modes (#1018)
==============================

The staged-execution Pexec modes are 68k TOS/FreeMiNT compatibility, not a
native launch API. pTOS has not released 1.0 and makes a clean break:

Targetless modes (5/7/4/6/104/106) carry no executable pathname, so neither
the caller's format nor the content of the basepage decides whether they are
allowed: an ELF program on m68k may use them like a PRG. A GO enters the
basepage the way TOS does, at p_tbase with the basepage address; there is no
ELF entry, no format dispatch and no retained PRG/ELF provenance check. What
remains is ordinary runtime safety: the basepage must be one the caller made
or loaded and still owns, not launched, stale or foreign, and every
allocation is rolled back on failure.

On MMU ARM and x32 the staged modes are refused with EINVFN before the
arguments are read (bdos/uaccess.c) and again at the GEMDOS entry
(xexec()), so no image is allocated and no ownership moves.

FreeMiNT (sys/k_exec.c, sys_pexec() and exec_region()) is the reference
for how 4/6/104/106 start a basepage. Every start enters at p_tbase with
A0 = 0, sp = p_hitpa - 0x28 inside the TPA and the basepage at 4(sp); the
program sets its own stack and Mshrink()s the rest, as on TOS. Modes 4 and
104 start a PROCESS sharing the caller's address space (4 waits for it, 104
returns its PID); 6 and 106 start one with an address space of its own,
which takes the basepage over.

The basepage may come from mode 3 (a PRG) or from mode 5/7. On the m68k MMU
kernels mode 5/7 gives a program basepage the classic TPA (the free memory,
up to 1 MiB, its end aligned), so a loader can put code in it, point
p_tbase there and start it. For such a basepage the shared-VM preparation
holds the TPA up to the end of the text, data and bss the caller states (at
least the basepage) and makes it executable; for a staged PRG it holds the
loaded image. Nothing holds the TPA above that, where the startup stack is,
so the child's Mshrink() can release it. A p_tbase that cannot run is not
refused: as on FreeMiNT, the child faults on it and the fault is its exit
status. MiNTLib's tfork() points p_tbase at a function of the caller.

Unlike FreeMiNT, a basepage starts once: the staged basepage becomes the
child, so a second 4/104 of it is refused (EIMBA), as is the caller's own
basepage or a running one. Each start forking a new PROCESS from a
caller-owned basepage, as FreeMiNT does, is a follow-up.

Non-MMU ARM is to be deprecated and is left unchecked: it has no user/kernel
boundary, so it keeps the staged modes exactly as before and does not tell
the kernel's requests from a program's. CONF_WITH_STAGED_PEXEC says where
the public staged modes exist (m68k, and kernels without user address
spaces).

Kernel-internal requests
------------------------
The kernel itself still creates basepages for, and starts, code it carries:
the ROM shell (exec_os), the built-in and early EmuCON, ROM programs the AES
runs (aes_run_rom_program()) and the NatFeats bootstrap; and the AES loads
desk accessories with a load-only request (pgmld()). On m68k and ARM these
requests must enter through the GEMDOS trap, whose return delivers a
reentrant launch's exit code to the right call site. They therefore use the
same dispatcher with PE_KERNEL set in the mode (include/bdosdefs.h). A
process with a user address space can never make such a request (refused in
uaccess.c and xexec()); a kernel without address spaces has no user/kernel
boundary to enforce, so there the bit is never put in the mode word
(PE_KERNEL_TAG, include/config.h): FreeMiNT, Hatari's GEMDOS hook and other
trap #1 filters see the TOS modes they know, and a program setting the bit
gets EINVFN as before. The one consequence is that the AES accessory load is
then an ordinary mode 3, PRG-only on m68k. PE_KERNEL requests never stage into a caller's heap and
never move ownership to a user caller: the caller has no address space. On an
address-space kernel a PE_KERNEL load (the x86-64 self-test harness) stages
the image into the new process's own address space.
