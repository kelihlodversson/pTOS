Internal clone startup: leases and publication gates (#892)
=========================================================

This is a construction contract, not a runnable clone implementation. Public
Pclone remains validation-only. KTHREAD.identity_only, backend-install/start
checks and proc_clone_commit's startup gate remain in place. Preparing a CPU
image is not a CPU/FPU context-switch or preservation test.

Concrete ownership
------------------

PROC_CLONE_TRANSACTION owns source/target identity references, its KTHREAD and
shared construction KASPACE. Its optional THREAD_STARTUP_DRAFT owns another
KASPACE reference, the copied kernel arguments, exact optional PID/TID output
addresses, five possible mapping leases, a backend CPU/FPU image, two distinct
kernel stacks, and at most one reversible generic lifecycle registration.
Each mapping lease independently retains KASPACE; list membership is borrowed.
There are no PROCESS/ASPACE/THREAD reference cycles or user-owned handoff records.

The scheduler stack and syscall stack are still separate resources. Neither
has executed in this draft. Cancellation frees each through its existing owner.
Nothing is installed into KTHREAD or the scheduler. Transaction abort cancels
the draft before releasing THREAD/PROCESS/ASPACE and factory ownership.

Mapping lease contract
----------------------

kaspace_lease_acquire requires resident USER mappings with the requested WRITE
and/or EXEC permissions. It never backs lazy pages, performs COW or writes user
memory. The caller must complete those potentially fallible operations first.
Missing residency/permissions fail rather than allocating behind validation.

Entry and return leases cover their entire mapping pages. The stack lease
covers the entire supplied range, rounded out to pages: the return slot,
128-byte red zone, discarded alignment bytes and future stack reservation all
fit within it. The x32 builder still checks the actual function-entry frame.
Optional PID and TID outputs are each a four-byte aligned 32-bit destination.
They cannot overlap each other, the supplied stack, or entry/return code pages.
Output preparation additionally uses the same RAM/direct-map safety preflight
as aspace_copy_to_user; a device translation alone is insufficient.

A preparation lease is REVOCABLE. Every overlapping mapping or permission
mutation first marks it permanently revoked. Restoring permissions or unmapping
and remapping the same VA, even to the same physical page, cannot revive it.
The lease's non-wrapping revoked bit belongs to its live kernel allocation; there
is no finite global generation counter which can wrap back to a valid value.
Translation checks also reject currently invalid access, but are not the identity
proof. The backend mutation barriers supply that proof. Only a fresh acquisition
can authorize a replacement mapping.

kaspace_lease_seal validates a complete set before sealing any member. It neither
allocates nor invokes callbacks. SEALED leases reject an overlapping mutation
before changing any lease or mapping. A failed group seal seals no member.
Preparation may span cooperative scheduling points, but sealing starts a short
serialized no-yield, no-user-entry, no-callback critical window. This checkpoint
can only leave that window by aborting. It cannot dispatch an execution image.

Mutation audit (both the x32 and common ARM/m68k ASPACE backends):

* Mmap cannot replace a resident leased range. Subsequent backing is covered by
  map_page/map_private/fault_in/fault_file barriers.
* Munmap validates its complete requested span against sealed leases before
  touching any region. release_lazy/unmap_private also check the backend barrier.
* Mprot checks before changing logical metadata or PTEs. Even restoring the same
  permissions cannot resurrect a revoked preparation lease.
* Ordinary Mfree/Mshrink release pages before deleting/changing KASPACE heap
  metadata. A sealed overlap fails without that ledger mutation. Unsealed release
  revokes the lease; later heap reuse cannot revive it.
* Already-resident anonymous faults do not change identity. Absent-page backing
  passes the mutation barrier. A leased page cannot be absent at acquisition.
* File COW checks before I/O/allocation/PTE replacement. A sealed range refuses
  the replacement; an unsealed attempt conservatively revokes even on later OOM.
* move_private checks source and target ranges before transferring pages.
  Loader borrows, grants and procmem mapping/shrink/release use the same barrier.
  The void compatibility APIs unborrow/shrink have no recoverable rejection
  result: calling them during an overlapping seal is a fail-stop invariant
  violation. No callback or such cleanup is allowed inside the sealed window.
* Each lease retains its backend through KASPACE, so normal final destruction
  cannot bypass a live lease. Shutdown uses release_lazy and honors its refusal.

Rejected mutations can conservatively revoke unsealed leases before discovering
another invalid argument or a later failure. False rejection is safe; silently
revalidating a changed mapping is not. Callers abort/reprepare after revocation.
Physical procmem ownership, pins and deferred reclamation are unchanged.

Publication state machine
-------------------------

  CONSTRUCTED -> PREPARED -> OBSERVED -> SEALED -> COMMITTED -> RUNNABLE
  identities     image      observer   leases    outputs/      scheduler
                 + stacks   + optional protected ownership     visibility
                 + leases   outputs

CONSTRUCTED is the transaction before a draft exists. PREPARED is real image,
stack and entry/return/stack lease ownership. Optional output preparation is
all-or-nothing in PREPARED. OBSERVED means a kernel observer has successfully
registered and transferred one rollback obligation. It is generic, not CUIS.
Failed registration must unwind its own partial work. Callbacks must not yield,
unwind, reenter or cancel their transaction. A mapping change during successful
registration is detected, and registration is released before returning failure.

SEALED rechecks current mappings and seals startup and output leases together.
COMMITTED and RUNNABLE are deliberately UNREACHABLE reserved states. Even an
observed, sealed draft returns EINVFN at publication_check/clone commit; revoked
mappings return EIMBA. Results and every user destination remain unchanged.
No return-slot store, identity output store or scheduler insertion exists here.

The future final transition must pre-register observers/leases, resolve all
allocation/I/O/backing/context failures, recheck source/target PROCESS state,
then seal and revalidate outputs immediately before a no-fail commit. It must
have one owner for every context/stack, prevalidated no-fault RAM destinations,
and prepared scheduler storage. After the first externally visible output store
there can be no fallible allocation/callback/rollback. Ownership transfer and
scheduler insertion must occur without yields or mapping mutation in between.
The scheduler must never observe the intermediate committed-but-unpublished
THREAD. No rollback is allowed after dispatch.

Before enabling timer preemption/SMP, #713 must provide synchronization for: registry lookup, lease acquisition/revocation/sealing, PROCESS
state, observer cancellation, user outputs and scheduler publication must share
a proved exclusion/ordering contract. The current implementation relies on the
existing cooperative/no-mapping-mutation-in-interrupt context. No new scheduler,
locks or unproved atomic multiword-publication claim is introduced here.

The execution backend must then take over kernel stacks and an execution-lifetime
user-stack reservation/hold before releasing startup seals. That long-lived hold
must not use the short no-callback seal window as a substitute for lifetime
management. Entry/return startup leases can be released only once the startup
boundary is irrevocably crossed; output leases only after stores are complete.
Cancellation before that boundary releases all leases. This checkpoint has no
successful startup and therefore releases all leases on abort only.

Trusted return/termination bridge gate
-------------------------------------

The backend owns an immutable, kernel-selected single-THREAD PROCESS return
bridge, described below. There is no caller-supplied return PC. That bridge uses
the existing whole-PROCESS Pterm path and is not a thread-only exit capability.
SAME_PROCESS dispatch must wait for sibling-safe internal #893 termination;
a distinct-PROCESS/sole-THREAD context still requires controlled CPU/launcher
integration and atomic publication. None of the startup or identity-only guards
has been removed. Public group exit, joins, waits and TLS remain downstream.

Rollback, aliases and limitations
--------------------------------

Before publication, abort consumes the canonical handle first, releases mapping
leases (leaving any sealed window), unregisters a successful observer once, frees
both never-used kernel stacks/image, releases the backend bridge capability,
and releases KASPACE. Transaction abort
then releases the remaining THREAD/PROCESS references and factory resources.
Filesystem cleanup still obeys the documented bounded-close/no-unwind fail-stop
contract. Failed prepare/observe/seal leaves outputs untouched. Repeated calls
through consumed handles are harmless; borrowed aliases are never ownership
handles and may not be used after abort. Arbitrary dangling C pointers are not a
supported handle-recovery interface.

No public runnable sibling, thread-only return capability, clone context switch,
executing clone CPU/FPU preservation test, output commit, scheduler publication
or runnable stack-lifetime transfer is claimed by this checkpoint.

Kernel-selected bridge and execution holds
-----------------------------------------

THREAD_STARTUP_ARGS contains no return PC.
The x32 backend receives an opaque kernel-created return-bridge capability,
checks that its ASPACE matches, and derives the PC itself. A coincidentally
identical executable page at the reserved VA is rejected rather than adopted.

The bridge occupies the final user page, outside mmap/heap/callback windows.
Its exact kernel instruction image and effective USER|EXEC (not WRITE) access
are checked. A privately owned durable mapping hold prevents replacement or
permission changes for the capability's entire lifetime. A borrowed registry
shares one mapping among drafts in the same KASPACE; reference-count exhaustion
fails. Final capability release drops its hold, removes the code page and its
metadata, and releases KASPACE. Ordinary backend page-table capacity remains
reusable until final ASPACE destruction, as with existing unmap; this is not a
claim that every failed attempt reduces page-table capacity immediately. Tests
prime that capacity before per-attempt snapshots and verify the exact complete
ASPACE lifetime baseline after all owners are gone.

The current internal bridge ABI is deliberately SINGLE-THREAD PROCESS exit:

  LONG entry(void *argument) -> EAX result
  bridge: EDI = EAX; RAX = (GEMDOS class 1 << 32) | Pterm 0x4c; syscall; ud2

The existing Pterm UWORD status contract takes the low 16 bits. No C frames,
user input PC, new syscall, parallel termination mechanism, or public Pterm
semantics are introduced. An unexpected return from Pterm executes UD2.
The bridge uses the existing xterm -> termuser -> resumed launcher -> common
proc_finalize_exit ordering, off the terminated syscall stack. Scheduler-root
reap of a managed task's separate scheduler stack remains independent.

Production QEMU tests execute a real normal RET and an entry UD2 through that
EXISTING launcher, with another PROCESS identity retaining the same ASPACE.
They verify status, the four safe-handoff stages, independent peer identity,
retained mappings, duplicate release, final code-page removal and resource
baselines. The membership preflight rejects two THREADs in the same PROCESS.
This is NOT dispatch of a constructed proc_clone CPU/FPU image and NOT an
implementation of sibling-only termination. Public and trusted clone startup
publication remain disabled. The existing xterm guard remains intact.

Durable mapping holds are distinct from short publication seals. A hold is
allowed across callbacks, scheduling points and user execution. It requires
privately owned resident non-file-cache pages; borrowed/procmem mappings and
unresolved file COW cannot acquire it. kaspace_stack_hold_acquire additionally
requires ordinary KASPACE heap or anonymous mmap reservations, never loader
staging, loans, file-backed views, or the original THREAD's implicit stack-growth
reservation. Backing remains explicit and fallible before publication.

KTHREAD can consume exactly one such stack-hold handle while constructed. It
retains KASPACE independently and rejects a foreign-space or duplicate transfer.
After stop, safe-context reap invokes the backend reclaimer first, then releases
the user-stack hold, then membership/ASPACE/PROCESS references. Releasing a hold
does not free caller-owned Malloc memory: it makes ordinary release legal again.
Final ASPACE ownership releases remaining reservations. Tests prove two THREADs
retain one reservation, first detach cannot permit Mfree, final detach permits
it, borrowed-page/OOM construction rolls back, and unchanged identity-only
start guards reject execution. Transaction cancellation releases the backend
before KTHREAD drops its independently retained user-stack hold.

The x32 backend can also detach its two kernel stacks into an initialized empty
X32_THREAD_STACK_OWNERS. This moves each physical/top pair once; image cancellation
then owns neither stack. The syscall owner must release after launcher handoff;
the scheduler owner only after root handoff. Production tests perform transfer,
image cancellation, separate exactly-once release and verify the current SP is
outside both stacks. They do not assert an executing clone handoff exists yet.

Remaining publication blockers are concrete:

1. SAME_PROCESS requires #893's INTERNAL thread-only stop/handoff/last-thread
   decision; this Pterm-based bridge is not that capability. No shared-process
   context may be enabled using it merely because the membership once was sole.
2. A distinct PROCESS/one-THREAD clone still needs to bind the prepared full
   CPU/FPU image, syscall stack and launcher continuation to the existing native
   task. The legacy gouser entry is not a consumer of this CPU/FPU image. The
   current clone_identity_only and KTHREAD.identity_only guards remain.
3. That backend must preallocate scheduler storage, take bridge/user/kernel stack
   owners and lifecycle registrations, then commit no-fault frame/output stores
   and scheduler insertion as one no-fail serialized transition. No stores or
   scheduler publication have been added. COMMITTED/RUNNABLE are unreachable.

The six-stage state machine above remains the intended transition. All mapping
holds, context/bridge construction, observer registration, output preflight and
scheduler-capacity reservation must precede sealing and the first visible store.
After that store: no callback, allocation, yield, failure or rollback. #713 must
supply exclusion before preemption/SMP; no unproved concurrency model is assumed.
Actual CPU/FPU preservation of a new context must be tested once dispatch is
connected. Current FPU-image inspection and legacy launcher runtime coverage
must not be described as that future test.
