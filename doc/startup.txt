A few notes on the EmuTOS startup sequence
==========================================

The EmuTOS startup sequence is similar to that of Atari TOS.  The
following keys affect startup:
   Alt: set floppy A: as boot device instead of first disk partition
   Esc: run an early console
   Ctrl: start up as a 'bare' system:
        do not use any Nova/ET4000 card present
        do not run AUTO folder programs
        do not load user-defined mouse cursors
        do not load desk accessories
        do not run an autorun program
        do not load desktop icons
        do not use the EMUDESK.INF file for desktop setup

Details
-------
Note: in the following, all files referenced must be in the root
directory of the boot device.

1. After some basic system initialisation, if a diagnostic cartridge
   is present, it is run.

2. ST RAM is initialised, then the BIOS and the rest of the hardware
   is initialised.
   An optional cold boot delay (1-255 seconds) can be configured by the
   user by changing a value in the extended OS header (OSXH) in the ROM
   image. EmuTOS then waits the configured amount of time before
   accessing any block devices (floppy disks, hard disks, etc.).
   See doc/version.txt for details.

3. On ROMs other than 192K, the code checks for the presence of a
   Nova/ET4000 video board.  If detected, the video output is directed
   to it (this may be skipped by pressing the Ctrl key during startup).

4. If a cartridge is present, any type 3 cartridge applications are
   run (under Hatari, this is where GEMDOS emulation is set up).

5. On a cold boot only, the EmuTOS welcome screen is displayed.
   While the screen is displayed, the keys Alt, Ctrl, and Esc may be
   pressed to alter subsequent processing (see below).

6. If the user pressed the Alt key in step 4 above, the boot device
   is set to the first floppy (drive A:).  Otherwise it is set to
   the first partition of the first device found.  Devices are scanned
   in the following sequence: IDE, SCSI, ACSI, SD/MMC.

7. If the user pressed the Esc key in step 4 above, the Emucon2 console
   is displayed (on exit, the startup will continue as below).

8. All PRG programs in the AUTO folder are run, in directory sequence.
   This is skipped if the Ctrl key was pressed in step 4 above.

9. The AES is started.  If an EMUDESK.INF file is present, it is
   checked for a video setting (a #E line).  If a setting is specified,
   and it differs from the current setting, the current display mode
   is changed.

10. The AES is initialised.  If an EMUCURS.RSC file is present, user-
   defined mouse cursors are loaded from it.  This is skipped if the
   Ctrl key was pressed in step 4 above.

11. Desk accessories are loaded, if present.  This is skipped if the
   Ctrl key was pressed in step 4 above.

12. If an EMUDESK.INF file is present, it is checked for an autorun
   program setting (a #Z line).  If an autorun program exists, it is
   run.  This is skipped if the Ctrl key was pressed in step 4 above.

13. The desktop is started.  If an EMUICON.RSC file is present, user
   desktop icons are loaded from it.  This is skipped if the Ctrl key
   was pressed in step 4 above.

14. If an EMUDESK.INF file is present, it is used to set up the
   desktop display.  This is skipped if the Ctrl key was pressed in
   step 4 above, and a default display is set up instead.

At this point, desktop initialisation is complete, and EmuDesk waits
for user input.

First native MMU program (#1039)
--------------------------------
Routing audited at epic/889-process-scheduling commit cb868b1f9. When
CONF_WITH_NATIVE_SCHED is enabled, the boot controller can call ordinary
Pexec(0) even with a parked root and existing independent tasks.
bdos/proc.c routes the loaded image to ksched_exec(). The dispatcher
prepares a PROCESS, initial THREAD, address space and execution stacks
before publishing it. The boot caller waits on a kernel admission result
and receives the full 16-bit exit code. It never acquires a user THREAD
identity. Failure before publication rolls back the admission and the
loader drops the executable and inherited file and directory references.

Entry path                            Execution and ownership
-----------------------------------   ------------------------------------
AUTO and COMMAND.PRG (all MMUs)       bios.c loads with mode 0. USER anchor.
External CLI, including early CLI     bios.c try_shell uses mode 0 on all
                                      three MMUs. USER anchor.
External desktop or AES on x32        The boot shell is a disk program
                                      loaded by try_shell. USER anchor.
                                      The desktop's managed launches use
                                      its existing CUIS admission.
Embedded x32 EmuCON                   start_builtin_cli installs a native
                                      image and uses internal mode 6.
                                      USER anchor. ARM/m68k per-process
                                      MMU profiles require external CLI.
Ordinary mode 0 from a managed THREAD Independent USER anchor, with the
                                      caller's exact-child wait (#1015).
Mode 100                              Independent USER anchor. Returns a
                                      PID for the existing PROCESS wait.
Mode 200, where enabled               Replaces the current PROCESS image
                                      under its own admission. It is not
                                      a source of a new PROCESS identity.
binfmt and shebang interpreters       bdos/proc.c resolves the image
                                      before launch. The interpreter
                                      takes the resolved mode 0 or mode
                                      100 path. Native image interpreters
                                      use the same THREAD and address
                                      space as their main executable.
True ROM and kernel entry             The boot controller and marked x32
                                      exec_os entry have no USER anchor.
                                      The legacy AES ROM profiles have
                                      no per-process MMU scheduler.
Legacy accessories and callbacks      Accessory and callback entry use
                                      their own guarded launch or borrowed
                                      execution context. No independent
                                      anchor is granted by that entry.
Deliberately nested launch            May have an associated THREAD, but
                                      remains on the enclosing task's
                                      carrier. No dependent admission.
Legacy, scheduler-disabled kernels    Continue to use existing launch
                                      paths without a native anchor.

Pclone and Pthjoin require their respective feature gates. With the gates
on, an ordinary program started as an anchor can create separate PROCESSes
or sibling THREADs sharing its address space, including on the first launch.
Those executions have their own TIDs and stacks. Pthjoin consumes sibling
completion and Pwaitpid consumes child PROCESS completion. The capability
comes from the authenticated anchor and PROCESS, independently of whether
some unrelated scheduler task already exists.

The regression boot disk starts FIRST.TOS through the ordinary boot
Pexec(0) call before the global scheduler fixture or shell. It runs the
same file via both launch controls, checks fault and normal completion,
and uses the existing test hooks to check owner counts and launch rollback.
At the audited baseline CONF_WITH_EXIT_HANDOFF_TEST forced the first
synchronous launch from a managed caller onto an untracked carrier. The
test now explicitly selects a separate nested launch to exercise the
refused handoff and the Pclone guard.
