Shared-loader stack and inherited limits (test-gated consumer)
------------------------------------------------------------
Preparation snapshots the source PROCESS priority, CORE/DATA limits and effective
stack cap. Commit assigns them without a new fallible step; aborted preparation
does not change the staged PROCESS policy. The shared child uses its independently
retained, guarded resident heap stack, capped by the inherited stack limit. This
is a bounded startup extent, not an implementation of lazy growth to that cap.
Interpreted argc/argv/AUXV construction fits within the actual body and leaves a
resident page below it for runtime use; excessive startup data fails preparation.

The inherited scalar cap does not authorize a synthetic top-of-VA stack. Shared
children obtain backing only from their actual heap/mmap or authenticated retained
reservations. Callback stack bounds use the actual body. Querying the stack cap
and setting the same normalized cap succeed; relocating/resizing this sealed
stack returns EACCDN. Nested shared launches duplicate existing reservation holds
rather than inventing a new default-stack owner.

Launch cleanup and ordinary mapping ownership
--------------------------------------------
A rejected launch grants no cleanup right over an existing target attachment.
The launch scope may abort only preparation it successfully acquired. In the
supported cooperative no-yield preparation/abort path, constructor rollback and
scope cleanup are idempotent; committed sets with resumable THREADs remain
protected by the existing fatal invariant.

Ordinary KASPACE heap/mmap lifetime uses #968's canonical memberships and
exact attachments. The former all-visible-region R2 sweep is removed. Claims
are prepared before borrowing/staging or opening the permission journal, and
moved exactly once into the clone transaction. Commit moves membership at its
existing no-fail boundary. Abort restores the journal after releasing its own
conflicting special holds, before canonical claim release may call file cleanup.
The staged image remains caller-owned and retryable. Failed competing attempts
cannot consume an existing preparation token or committed attachment.
File-backed mmap retains its live birth, exact bounds, logical rights and
FILE_BACKING owner; missing pages and file-COW remain materializable only through
that authenticated owner. Attachment tickets provide lifetime, not permission. KPROC-only image/raw/
stack views retain captured receipts. No cleanup fence, broad source image hold
or merely readable PTE grants new file-backing authority.

FreeMiNT compatibility and explicit runtime ownership
---------------------------------------------------
FreeMiNT's mode4/104 shares ALL parent memory, not just the initial snapshot.
Its share_mem() returns the same p_mem; future Malloc/Mxalloc records attach to
that shared memspace, which is released only at its last link. A surviving
sharer can access allocations created after sharing even after their creator
exits. Pexec4/104 therefore inherits GENERAL lifetime membership, including
future ordinary Malloc and unannotated pTOS Mmap allocations. Existing image,
basepage, environment, interpreter and actual stack retain their R1-R4 claims.

Primary reference: FreeMiNT68be4e529ad82ea9ec2b1c215b53303f91e78d52:
  doc/programmer/mint.txt1115-1118,1295-1297 (all memory, basepage/environment)
  sys/k_fork.c143-146; sys/proc_help.h43-47 (shared p_mem)
  sys/memory.c524-552; sys/proc_help.c224-261 (late allocation, final link)
These are not evidence that FreeMiNT implements pTOS's mmap API: its
sys/syscalls.master514-515 lists mmap/munmap as undefined.

MAP_PTOS_RUNTIME is an explicit pTOS loader-owned lifetime annotation, admitted
and emitted by ld.so ONLY with CONF_WITH_SHARED_VM_PEXEC_TEST. It is not an
implicit change to general FreeMiNT allocations or a production ABI activation.
Each loaded standard-entry PROCESS prepares a fresh RUNTIME scope before THREAD
publication. Its annotated anonymous/file maps join that scope. Existing exact
source-owned runtime dependencies are attached to a new loaded child; unrelated
visible KASPACE mappings and future foreign runtime allocations are not inherited.
General allocations remain common even when created by a departed interpreter.

Generic CLONE_VM inherits GENERAL and RUNTIME memberships and the source's
selected runtime scope, retaining existing AND future compatible runtime maps.
Thus a generic peer created before the creator's next DSO allocation still owns
that allocation. Creator exit cannot revoke the peer's live code/data. A loaded
PROCESS has a separate runtime allocation scope; merely passing a pointer to
another scope does not export lifetime. Trusted cross-scope retention uses
#968's authenticated exact attachment API, with destination acquired before
source release. A PRIVATE_VM snapshot binds copied classification to fresh
memberships and preserves an empty runtime selector for future allocations.

Runtime membership retires after the final THREAD stops, independently of
Pwaitpid or final root destruction. Final claims release canonical mappings and
FILE_BACKING exactly once; immutable #958 backing bounds and access checks still
apply. No parallel mapping registry, reaper or scheduler is introduced. The
shared region limit remains96. Whole-consumer public compatibility acceptance
and fresh native resource/DSO evidence are required before public activation.

Generic shared-root execution dependencies
------------------------------------------
Generic NEW_PROCESS descendants need more than ordinary mapping membership:
DSO code can call an interposed function or syscall stub in the source's main
image. Final source exit must not allow its original staged metadata to be
freed while that peer can execute such code. Generic same-root construction
therefore duplicates the existing bounded R1/R2 receipts and authenticates the
immediate source's own compatibility metadata and main/interpreter witnesses.
A mutually exclusive inherited role uses the same shared_exec_regions storage
(one set per PROCESS, the unchanged raw/region bounds); it carries no borrowed
stack owner, permission journal, pending image, parent/controller or image-commit
state. Each token is duplicated through its canonical primitive, never copied.

This role is prepared after mapping-owner admission and before THREAD creation,
committed at the existing identity-only adoption or runnable no-fail boundary,
and released after final THREAD stop before ordinary membership retirement.
Loaded entry/guarded-stack/RELRO and scalar-limit rules remain exclusive to the
loaded role. SAME_PROCESS adds no PROCESS owner; PRIVATE_VM copies its root and
never inherits source-root receipts. A failed prefix releases only its acquired
tickets and leaves source receipts, mappings, aliases and permissions intact.

exit, including a call back into the source image, then checks exact45-counter
conservation with the parent root alive. The original failing control is retained
