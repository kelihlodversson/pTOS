Installing:

You will need a (cross-)GCC toolchain for the machine you are building for:

  Atari, ARAnyM, Amiga, ColdFire (m68k)
      Vincent Rivière's m68k-atari-mintelf ELF-based tools, which is what
      the build expects by default:
      http://vincent.riviere.free.fr/soft/m68k-atari-mintelf/

      On Debian and Ubuntu they are packaged, which is by far the quickest
      way to get a working toolchain:

          sudo add-apt-repository ppa:vriviere/mintelf
          sudo apt-get update
          sudo apt-get install cross-mintelf-essential

      The CI build installs this package from the same PPA too, plus the
      older cross-mint one for the a.out choice and the tools "make
      release" needs, see .github/actions/setup-toolchain/action.yml.

      Three m68k toolchains are offered, chosen under "m68k toolchain"
      in the Toolchain menu:

          m68k-atari-mintelf    the newer ELF based tools, the default,
                                http://vincent.riviere.free.fr/soft/m68k-atari-mintelf/
          m68k-atari-mint       the older cross-mint a.out tools,
                                http://vincent.riviere.free.fr/soft/m68k-atari-mint/
          bare m68k-elf         a plain m68k-elf toolchain, no MiNT at all

      Picking one selects both the compiler prefix and the flags it needs;
      there is nothing else to set.  The two ELF toolchains are built with
      -fleading-underscore, --register-prefix-optional and -DELF_TOOLCHAIN,
      which cross-mint does not want.

      Other toolchains, such as the old one from SpareMiNT, may also work.

  Raspberry Pi, QEMU 'virt' (ARM)
      Any bare metal arm-none-eabi toolchain, for example the one Debian
      and Ubuntu ship:

          sudo apt-get install gcc-arm-none-eabi

If your toolchain is installed under a name other than the one that goes
with the choice above, fill in "Cross compiler prefix override" in the same
menu.  It renames the executables only; the flags keep following the
toolchain you picked.  A one-off build can override it without touching the
configuration at all:

    make CROSS_COMPILE=m68k-atari-mintelf-

You will also need:

  * GNU make 4.3 or later (grouped targets are used; make 4.2.x will not work).
    macOS ships GNU Make 3.81 as /usr/bin/make; install GNU make with Homebrew
    and run gmake instead.
  * Python 3 with kconfiglib, which provides the configuration front ends:
        pip3 install kconfiglib


Configuring and building
========================

The build is configured the way the Linux kernel is.  You first pick one of
the ready-made configurations, optionally adjust it, and then build:

    make help                   # list the available configurations
    make atari512_defconfig     # start from one of them
    make menuconfig             # optional: adjust the configuration
    make                        # build the image

The chosen settings are stored in the file .config in the top directory.
From there, "make" generates obj/autoconf.h for the C code and
obj/auto.conf for the build system itself; neither should be edited by
hand.  Changing .config causes the whole image to be rebuilt.

"make menuconfig" opens a full screen menu in the terminal.  Every option
carries a help text, reachable with '?', and options that make no sense for
the selected machine are simply not offered.  "make guiconfig" does the
same in a window, if Tk is installed.

Other configuration targets:

    make oldconfig      ask about the options added since the last run
    make olddefconfig   accept the default value for every new option
    make savedefconfig  write a minimal ./defconfig for the current .config
    make allnoconfig    disable every optional feature
    make distclean      remove everything, including .config

To contribute a new configuration, adjust it with "make menuconfig", run
"make savedefconfig", and copy the resulting ./defconfig file to
configs/<name>_defconfig.

Raspberry Pi
------------

rpi1                kernel.img, for the Pi 1, Zero, A, A+, B, B+ and CM0
rpi2                kernel7.img, for the Pi 2B+
rpi3                kernel8-32.img, for the Pi 3, 3+ and CM3
rpi4                kernel7l.img, for the Pi 4 and 400

QEMU loads a kernel image directly and needs nothing else, but real
Raspberry Pi hardware does: the GPU reads its own boot firmware
(bootcode.bin, start*.elf, fixup*.dat) off the SD card before it ever gets
to loading a kernel*.img. The four kernel images above are named so the
firmware picks the right one and CPU mode for whichever board is plugged
in -- including kernel8-32.img's "-32" forcing 32-bit mode on the Pi 3, 3+
and CM3 even though those boards can also run 64-bit code -- so a single SD
card built from all four boots the whole Pi 1-4 lineup and no config.txt is
needed.

This combination -- the four kernel images plus the matching boot firmware,
fetched by tools/fetch-raspi-firmware.sh from a pinned, checksum-verified
commit of https://github.com/raspberrypi/firmware and redistributed under
its LICENCE.broadcom, which is included alongside them -- ships as two
files:

    ptos-raspi-<version>.zip       the loose files, to drop onto an SD
                                    card that is already partitioned and
                                    formatted
    ptos-raspi-<version>.img.zip   a raw disk image (MBR partition table,
                                    one FAT16 partition) that dd,
                                    Raspberry Pi Imager or balenaEtcher can
                                    write directly, with no manual
                                    partitioning or formatting

tools/mkraspi-image.sh builds the .img from a directory of files with
mtools and sfdisk alone, without ever mounting or loop-attaching anything.

Both GitHub Actions workflows produce them (see "Continuous integration"
below): build.yml keeps them as a workflow artifact of every push and pull
request, so a card to test a change on real hardware is one download away
without waiting for a release, and release.yml additionally attaches them
to every tagged release.

ARM virt
--------

virt-arm            virt-arm.elf, for QEMU's generic ARM "virt" board

The virt board is emulation only; there is no such physical machine.  It
gives the ARM port a target that does not depend on Raspberry Pi hardware
at all: a PL011 serial console, a GICv2 interrupt controller and the ARM
generic timer.  The image is an ELF file rather than a raw binary, because
RAM starts at physical 0x40000000 while EmuTOS is linked at the usual low
addresses, and QEMU's ELF loader is what places it correctly.  Run it with:

    make virt-arm_defconfig && make
    qemu-system-arm -M virt -cpu cortex-a7 -m 128 -kernel virt-arm.elf \
        -d guest_errors -serial stdio

Adding "-S -s" lets a remote gdb attach, as with the Raspberry Pi
configurations.

m68k virt
---------

virt-m68k           virt-m68k.elf, for QEMU's generic m68k "virt" board

Also emulation only, and also an ELF image for the same reason (QEMU's
-kernel loader), but otherwise unrelated to the ARM virt board above: no
Atari-compatible chipset, no MMU trick needed (this board's RAM already
starts at physical 0x0, where EmuTOS expects it). Console, interrupt
routing and the periodic tick come from three "Goldfish" devices (a TTY,
a PIC, and an RTC used as a one-shot alarm re-armed on every interrupt).
Run it with:

    make virt-m68k_defconfig && make
    qemu-system-m68k -M virt -m 128 -cpu m68020 -kernel virt-m68k.elf \
        -d guest_errors -serial stdio

Both flags after -M virt matter, not just the -kernel one: -m 128 is
required because the image hardcodes 128 MiB as the top of RAM (there is
no FDT parsing yet to size it from the command line), and -cpu m68020 is
required instead of the board's own m68040 default because this specific
QEMU version fatally aborts the whole VM -- instead of raising the guest
CPU exception EmuTOS's shared CPU-detection code expects and handles --
when that code probes a 68060-only register while telling 68040 and
68060 apart. m68020 detection resolves earlier in that same routine, so
it never reaches the register QEMU mishandles.


Countries and languages
=======================

The country selects the keyboard layout, the character set and the date and
time format.  It is picked in the "Localization" menu of the configuration.

A single-country image contains only the messages of that country, which
saves a large amount of space; this is what most configurations use.  Turn
"Build a single-country image" off to get an image that supports every
country and picks one at boot time, from the NVRAM if the machine has one,
and otherwise from the country code stored in the OS header.  The atari512,
aranym, firebee and prg configurations are multi-language.

The country can also be overridden for a single build, without touching the
configuration.  This is how the release archives are built for every
country in turn:

    make atari256_defconfig
    make COUNTRY=de UNIQUE=de

COUNTRY sets the country code in the OS header, UNIQUE restricts the image
to that one country.  Leave UNIQUE empty for a multi-language image.

Continuous integration
======================

GitHub Actions builds the tree on every push and pull request to master.
The workflows live in .github/workflows:

build.yml       builds every configuration in configs/ as a job of its own,
                so a failure names the machine it broke, and builds the m68k
                release archives and the Raspberry Pi SD card image (see
                above).  Every image is kept as a workflow artifact.
release.yml     publishes a GitHub release.  It runs when a version tag such
                as v0.1.0 is pushed, and can also be started by hand, which
                publishes a snapshot prerelease instead.

Both get their toolchain from .github/actions/setup-toolchain, which is the
authoritative list of what a build needs installed.  Adding a configuration
to configs/ is enough to have it built; the matrices are derived from that
directory rather than listed in the workflows.


Adding a configuration option
=============================

Options live in the Kconfig file of the directory they belong to
(bios/Kconfig, vdi/Kconfig, ...), or in one of the top level Kconfig.*
files for the machine, the image format and the localization.  A bool
option named CONF_WITH_FOO becomes "#define CONF_WITH_FOO 0" or
"#define CONF_WITH_FOO 1" in the generated header, so the sources can test
it with #if even though -Wundef is in effect.

Options named MACHINE_* and TARGET_* are only defined when they are set, so
that they can be tested with #ifdef, and options named BUILD_* never reach
the C code at all.

To make a source file conditional, add it to the obj-y list of the
directory it lives in with the matching option, Linux style:

    obj-$(CONF_WITH_FOO) += foo.o
