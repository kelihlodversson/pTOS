Installing:

You will need a (cross-)GCC toolchain for the machine you are building for:

  Atari, ARAnyM, Amiga, ColdFire (m68k)
      Vincent Rivière's m68k-atari-mintelf ELF-based tools, which is what
      the build expects by default:
      http://vincent.riviere.free.fr/soft/m68k-atari-mintelf/

      On Debian and Ubuntu they are packaged, which is by far the quickest
      way to get a working toolchain:

          sudo add-apt-repository ppa:vriviere/mintelf
          sudo apt-get update
          sudo apt-get install cross-mintelf-essential

      That PPA's gcc has no -mfastcall, which the CONF_WITH_MFASTCALL
      configurations need.  The CI build therefore uses only Thorsten
      Otto's prebuilt m68k-atari-mintelf toolchain (gcc, binutils and
      mintlib from https://tho-otto.m68k.eu/crossmint.php), see
      .github/actions/setup-toolchain/action.yml; it works for every
      m68k configuration.

      Three m68k toolchains are offered, chosen under "m68k toolchain"
      in the Toolchain menu:

          m68k-atari-mintelf    the newer ELF based tools, the default,
                                http://vincent.riviere.free.fr/soft/m68k-atari-mintelf/
          m68k-atari-mint       the older cross-mint a.out tools,
                                http://vincent.riviere.free.fr/soft/m68k-atari-mint/
          bare m68k-elf         a plain m68k-elf toolchain, no MiNT at all

      Picking one selects both the compiler prefix and the flags it needs;
      there is nothing else to set.  The two ELF toolchains are built with
       --register-prefix-optional and -DELF_TOOLCHAIN, which cross-mint does
       not want.

      Other toolchains, such as the old one from SpareMiNT, may also work.

  Raspberry Pi, QEMU 'virt' (ARM)
      Any bare metal arm-none-eabi toolchain, for example the one Debian
      and Ubuntu ship:

          sudo apt-get install gcc-arm-none-eabi

  PC (x86-64, UEFI boot)
      This target needs a toolchain whose *linker* supports the PE32+
      ("i386pep") emulation, not just ELF: the final link step runs
      "ld -m i386pep" directly (see the ARCH_X86_64 rule in the top level
      Makefile) to produce the PE32+ image UEFI firmware itself loads. A
      plain ELF-only cross binutils -- for example a from-source
      x86_64-elf toolchain built the way most "OS dev" GCC cross-compiler
      guides describe, with a bare --target=x86_64-elf and no extra
      --enable-targets -- does *not* include that emulation and fails
      with "unrecognized emulation mode: i386pep" at link time. Always
      confirm before relying on one:

          <prefix>ld --help | grep i386pep

      The pc-x86_64 configuration defaults to the x86_64-elf- prefix, so
      it never relies on the host compiler.  Override CROSS_COMPILE when
      your compatible toolchain uses another prefix.  On a Linux/x86-64
      host, the system gcc/binutils can be selected explicitly:

          make CROSS_COMPILE= pc-x86_64_defconfig && make CROSS_COMPILE=

      On any other host, two toolchains are known to work:

      * a Debian/Ubuntu-packaged x86_64-linux-gnu cross toolchain (built
        from the same binutils source as the native x86-64 package, just
        cross-hosted, so it keeps the same PE emulations):

            sudo apt-get install gcc-x86-64-linux-gnu binutils-x86-64-linux-gnu

      * an x86_64-w64-mingw32 (MinGW-w64) cross toolchain, which is
        PE-native and therefore always has i386pep support. Its GCC
        defaults every function to the Microsoft x64 calling convention
        (it targets Windows), which conflicts with the SysV AMD64
        convention this port's hand-written assembly (relocate.S)
        assumes for ordinary internal calls -- add "-mabi=sysv" to
        CPUFLAGS (Kconfig) to restore that default globally, leaving
        only the functions efi.h explicitly marks "ms_abi" using the
        Microsoft convention.

      Either way, set "Cross compiler prefix override" (below) to the
      toolchain's prefix. To boot-test the image, you will also need
      QEMU and an OVMF UEFI firmware build:

          sudo apt-get install qemu-system-x86 ovmf

  PC (x86-64, EmuCON)
      On x86-64 EmuCON is not linked into the 64-bit kernel: "make" also
      builds it as an x32 ELF executable (obj/x32/emucon.elf, from the
      shared cli/ sources, in their standalone-console mode, with the small
      runtime in cli/x32/).  By default (CONF_EXTERNAL_CLI) it is copied to
      cli/emucon.tos and has to be on the boot drive, as EMUCON.TOS in the
      root directory of the EFI system partition; the kernel loads it from
      there and runs it as an ordinary ring-3 process.  Without the option
      the EFI image embeds it instead.  The boot self-test's probe program
      (tests/x32_probe/) is built and embedded the same way.  The compiler
      therefore needs the same x32 support described for the test program
      below; on Debian/Ubuntu that is the gcc-multilib package.  It uses
      the same cross compiler prefix as the kernel by default.  Set
      X32_CROSS_COMPILE explicitly only when the x32 compiler differs.
      The AES and EmuDesk are not available on this machine yet.

  PC (x86-64, running an x32 program from EmuCON)
      EmuCON runs a program by its ".tos" (".prg", ...) name whatever its
      executable format: the loader recognises an ELF by its contents.  To
      try the x32 test program, installed as X32HELLO.TOS, under QEMU/OVMF:

          make pc-x86_64_defconfig && make && make x32test
          mkdir -p esp/EFI/BOOT
          cp pc-x86_64.efi esp/EFI/BOOT/BOOTX64.EFI
          cp x32hello.elf esp/X32HELLO.TOS
          cp /usr/share/OVMF/OVMF_VARS_4M.fd .
          qemu-system-x86_64 -machine pc -m 256 -cpu qemu64,+pdpe1gb \
            -drive if=pflash,format=raw,readonly=on,file=/usr/share/OVMF/OVMF_CODE_4M.fd \
            -drive if=pflash,format=raw,file=OVMF_VARS_4M.fd \
            -drive format=raw,file=fat:rw:esp -serial stdio -display none

      then type "x32hello.tos" at the EmuCON prompt: the program runs in ring
      3, calls GEMDOS, exits, and the prompt comes back (it prints nothing on
      success).  The same file on the boot drive makes the boot self-test run
      it from a ring-3 process and print "x86-64 nested pexec: PASS"; CI does
      exactly that.

  PC (x86-64, x32 userspace test program)
      "make x32test" builds tests/x32_hello/x32_hello.c, the minimal x32
      psABI (ELFCLASS32 program headers, genuine EM_X86_64 long-mode
      instructions -- see issue #334) userspace test program, into
      x32hello.elf. This is a *separate* build from the kernel image
      above and needs a different toolchain: an ordinary ELF
      x86_64-linux-gnu (or x86_64-linux-gnux32) gcc with x32 multilib
      support, not the PE32+-capable one the kernel itself links with --
      neither of the two toolchains doc/install.txt recommends above for
      the kernel is guaranteed to have this (a MinGW-w64 cross toolchain
      has no x32 codegen at all; a distribution's x86_64-linux-gnu
      package may or may not ship the x32 multilib alongside it).

      On a Debian/Ubuntu x86-64 host, the native gcc/binutils already
      include x32 multilib support, so nothing extra needs installing
      there beyond the ordinary "gcc binutils" from the kernel's own
      section above -- confirm with:

          gcc -print-multi-lib | grep x32

      If it is missing, install it explicitly:

          sudo apt-get install gcc-multilib

      On any other host, point "x32 test-program cross compiler prefix"
      (below, in the Toolchain menu) at a cross toolchain with x32
      support instead -- for example a x86_64-linux-gnux32 triplet. This
      setting is independent of "Cross compiler prefix override" above:
      the two need not be, and often are not, the same toolchain.

      On macOS, Homebrew's x86_64-elf toolchain provides both the x32
      codegen and the x32 linker emulation:

          brew install x86_64-elf-gcc

      then build the complete EFI image with:

          make pc-x86_64_defconfig && make

      Note that the host "gcc" on macOS cannot build this at all: "-mx32"
      is an x86-64-ELF feature, so the compile fails on the 64-bit
      register names ("unknown register name 'rax'"). The prefix is
      therefore required rather than merely optional on that host. The
      build system already passes "-Wl,-m,elf32_x86_64" to name the
      linker's x32 output emulation explicitly, so no further flags are
      needed; without it a cross toolchain's driver can default to
      "i386:x86-64" and reject the x32 input with "i386:x64-32
      architecture of input file ... is incompatible with i386:x86-64
      output", even though the linker does support x32. You can check
      for that emulation with:

          x86_64-elf-ld -V | grep elf32_x86_64

      A successful link leaves one warning, "has a LOAD segment with RWX
      permissions". That is expected: the image is a single flat
      read/write/execute segment, which is what keeps the program down
      to the one PT_LOAD segment bdos/elfld.c maps.

If your toolchain is installed under a name other than the one that goes
with the choice above, fill in "Cross compiler prefix override" in the same
menu.  It renames the executables only; the flags keep following the
toolchain you picked.  A one-off build can override it without touching the
configuration at all:

    make CROSS_COMPILE=m68k-atari-mintelf-

You will also need:

  * GNU make 4.3 or later (grouped targets are used; make 4.2.x will not work).
    macOS ships GNU Make 3.81 as /usr/bin/make; install GNU make with Homebrew
    and run gmake instead.
  * Python 3 with kconfiglib, which provides the configuration front ends:
        pip3 install kconfiglib
  * The git submodules, for the configurations that use them:
        git submodule update --init
    lib/libcmini is used by the regression tests and EmuCON, lib/freetype
    by the scalable fonts (see below).


Configuring and building
========================

The build is configured the way the Linux kernel is.  You first pick one of
the ready-made configurations, optionally adjust it, and then build:

    make help                   # list the available configurations
    make atari512_defconfig     # start from one of them
    make menuconfig             # optional: adjust the configuration
    make                        # build the image

The chosen settings are stored in the file .config in the top directory.
From there, "make" generates obj/autoconf.h for the C code and
obj/auto.conf for the build system itself; neither should be edited by
hand.  Changing .config causes the whole image to be rebuilt.

"make menuconfig" opens a full screen menu in the terminal.  Every option
carries a help text, reachable with '?', and options that make no sense for
the selected machine are simply not offered.  "make guiconfig" does the
same in a window, if Tk is installed.

Other configuration targets:

    make oldconfig      ask about the options added since the last run
    make olddefconfig   accept the default value for every new option
    make savedefconfig  write a minimal ./defconfig for the current .config
    make allnoconfig    disable every optional feature
    make distclean      remove everything, including .config

To contribute a new configuration, adjust it with "make menuconfig", run
"make savedefconfig", and copy the resulting ./defconfig file to
configs/<name>_defconfig.

Scalable fonts (CONF_WITH_VDI_SCALABLE_FONTS, in the VDI menu) link the
FreeType library from the lib/freetype submodule into the image; the build
stops with a message if the submodule has not been fetched.  FreeType is
compiled with the image's own compiler and flags into obj/freetype-build,
with pTOS's configuration headers from vdi/freetype/ in place of its own,
so it needs nothing from the host's C library.  It adds about 285 KB on
m68k and ARM and 400 KB on x86-64, so the option is on by default only for
the images without a fixed size: the Raspberry Pi, ARM virt, m68k virt and
x86-64 kernels.  FreeType gets memory of the kernel's own, not GEMDOS's:
a pool of CONF_VDI_FONT_MEMORY KB (4 MB by default) set aside at start-up,
or the kernel heap on x86-64; font files are read into it whole.  It runs
on a 64 KB stack of its own.  CONF_DEBUG_FREETYPE_TEST_FONT (in the
debugging menu) names a font file to render at boot, to check all this on
a new machine.  FreeType is used under its GPL licence option (version 2
or any later version, the same terms as pTOS; see lib/freetype/LICENSE.TXT).
Work on the feature is tracked in #573.

With scalable fonts, pTOS also has a GDOS built in, which applications
recognise as SpeedoGDOS (vdi/vdi_gdos.c).  Once the AUTO folder has run,
vq_gdos() answers '_FSM' and an FSMC cookie with the magic '_SPD' and
version 4.00 and quality -1 (as fVDI's SpeedoGDOS mode) is installed
(not on x86-64, where programs cannot call the VDI).  vst_load_fonts() then adds the TrueType (*.TTF), OpenType (*.OTF)
and TrueType collection (*.TTC, each of its faces) fonts of CONF_VDI_FONT_DIR
(\GEMSYS\FONTS on the boot drive by default) to a workstation, and vqt_name() lists them after the system fonts with the
outline flag of SpeedoGDOS (intout[33] = 1).  Their font ids, from 10000
on, come from a hash of the font's name, so they stay the same from boot
to boot.  A GDOS loaded from the AUTO folder (NVDI, SpeedoGDOS, FontGDOS,
...) takes precedence: when trap #2 is hooked, or an FSMC or NVDI cookie
is there, the built-in GDOS stays out altogether and that GDOS works as
before.  GEM bitmap fonts (*.FNT, from ASSIGN.SYS) are left to such a
GDOS: the built-in one does not load them.

The font directory is scanned once, right after the AUTO folder has run.
A directory that is missing or empty gives a system with the bitmap fonts
only, and no error; if the scan found no font, the first vst_load_fonts()
looks again (for a drive that was not there at boot).  To add fonts, copy
the files to that directory under 8.3 names (the FAT volumes are read
without long names) and restart, or, with "Look for new scalable fonts
after vst_unload_fonts()" (CONF_VDI_FONT_RESCAN, on by default), let the
program that copied them call vst_unload_fonts() and vst_load_fonts():
the new files' fonts are then added after the existing ones, which keep
their index and id (a deleted font stays listed until the restart); to look elsewhere, change "Directory of
the scalable fonts" (CONF_VDI_FONT_DIR) in make menuconfig, with a drive
letter if the directory is not on the boot drive.  The style Regular,
Book, Roman and Normal is left out of a font's name ("DejaVu Sans", not
"DejaVu Sans Book").

The release images of the targets with scalable fonts (the Raspberry Pi SD
card image and archive) come with DejaVu Sans, Serif and Sans Mono, each
regular and bold, in \GEMSYS\FONTS as DJVUSANS.TTF, DJVUSANB.TTF,
DJVUSERF.TTF, DJVUSERB.TTF, DJVUMONO.TTF and DJVUMONB.TTF, with their
licence in LICENSE.TXT beside them.  The fonts are not part of the source
tree: tools/fetch-fonts.sh <dir> downloads them from the pinned DejaVu 2.37
release, checks them against checksums pinned in the script, and writes
them under these names (fonts/dejavu/LICENSE is the licence).  For an image
of your own, run it on the GEMSYS/FONTS directory of the files that go
into it.  The regression tests' disk gets the host's copies of DejaVu
under the same names (tools/run-regression-tests.sh).

A monospaced scalable font can be the system font (font id 1: the
console's, the desktop's, and that of every program that picks no other).
Set "System font" (CONF_VDI_SYSTEM_FONT) in make menuconfig to the file
name in the font directory, e.g. DJVUMONO.TTF; or, with no change to the
image, put a line SYSTEMFONT=DJVUMONO.TTF into \GEMSYS\PTOS.INF on the
boot drive, which takes precedence.  The font is rendered once at the
cells of the 8x8 and 8x16 system fonts, after AUTO programs have run and
before the AES starts; the 6x6 font stays the built-in one, and so does a
character the font lacks.  The font has to be monospaced, the character
set the Atari ST's, and no disk-based GDOS present; otherwise there is a
message on the console log and the ROM fonts stay.  The rendered forms
stay in memory for good.  With no setting nothing changes.

vst_font() then selects a scalable font, and vst_point() and vst_height()
set exactly the size asked for.  Each size is rendered whole by FreeType,
as a bitmap font of that size with the 256 characters of the Atari set,
so the text path draws it with all its writing modes, effects, rotation
and clipping (vdi/vdi_sfont.c).  Rendered sizes are kept up to
CONF_VDI_FONT_CACHE KB (1 MB by default); the one used longest ago that
no workstation has selected goes first.  Ink that reaches past a
character's advance width (an italic f, the foot of a j, anything slanted
by vst_skew(), a combining mark) is kept in cells of its own, which are
output after the characters of the string, transparently, from where each
character is: the advances and extents are still the advances, and a
character that follows does not cover that ink in replace mode (#607).

The built-in GDOS also answers the font calls SpeedoGDOS added, and those
NVDI added to them (opcodes 190 and 229 to 255, vdi/vdi_speedo.c; #577):
vqt_ext_name(), vqt_xfntinfo(), vst_name() and vqt_name_and_id(),
vqt_fontheader() (a virtual Speedo header); vst_arbpt(), vst_setsize()
(both also in their 32-bit forms), vst_width() and vst_skew(), which size
and slant a scalable font exactly; vqt_advance(), vqt_f_extent(),
vqt_real_extent(), v_ftext() and v_ftext_offset(); vst_kern(),
vst_track_offset(), vqt_pairkern() and vqt_trackkern(), the kerning being
that of a font's 'kern' table and applied to drawing and measuring alike;
vst_error(), vqt_cachesize(), v_flushcache() and vqt_get_table().
Advances are in whole pixels, as the characters are placed.  There are
no kerning tracks, no character bitmaps for v_getbitmap_info() (which
gives the advance only), no outlines for v_getoutline() (0 points), and
no cache file: v_savecache() and v_loadcache() fail.  As an extension,
vqt_cachesize(2) returns the bytes of font memory in use (the cache's free
bytes are 0 and 1's).  The FSMC cookie
stays at version 4.00: the calls of later versions are answered all the
same, and an application looks for NVDI's by trying them.

vst_map_mode() (and vst_charmap()) chooses what the WORDs of text are:
BICS (only its ASCII part is known), the Atari character set (the
default), Unicode's first plane (UCS-2, mode 2) or, as pTOS's own mode 3,
all of Unicode in UTF-16, a surrogate pair being one character.  An
application finds mode 3 by setting it and checking that vst_map_mode()
returns 3.  In Unicode, a scalable font is drawn in runs: ASCII from the
size itself, any other character from a page of 256 characters of that
size, rendered when first needed and kept in the same cache.  A character
the font lacks shows its missing-glyph shape, a lone surrogate the
replacement character.  The bitmap fonts keep the Atari character set: a
Unicode character is drawn as its Atari one, or as '?'.  In these maps,
vqt_width() answers -1 for a character the font lacks, whatever is drawn
for it, so that it tells which characters a font has.  vqt_char_index() converts
between the maps, its "direct" index being the BICS of mode 0, as
SpeedoGDOS has it, and not a font's own glyph index, so that what it
answers is drawn in mode 0 as the character asked about.  Only VDI text is
Unicode: the AES, the desktop and file names stay 8-bit.
tests/include/vdi_speedo.h has bindings for these calls, with gemlib's
names, for programs built against libcmini.

EmuCON as a program (CONF_EXTERNAL_CLI)
---------------------------------------

On the images that are loaded into RAM from a disk (rpi1-rpi4, virt-arm,
virt-m68k) EmuCON is not linked into the kernel: "make" also builds
emucon.tos, the standalone EmuCON of cli/Makefile (with the translations of
all languages, see "The LANG variable" in doc/nls.txt), and the kernel starts it with Pexec() from the root directory of the boot
drive, as EMUCON.TOS, when there is no AES to start (the CLI configurations),
for the early console (Esc at the welcome screen), and for the Console item
of the desktop.  If the file is not there the kernel says so on the console.

The file has to be on the boot drive.  "make test-dir" and "make test-hd"
put it there (the CLI regression runs boot QEMU on such a disk),
release-raspi-resources puts it on the card, and for any other disk it is
copied by hand.  Without a disk -- QEMU -kernel alone -- these images boot
and stop at "EmuCON: no shell in the root directory of the boot drive" (see
"Which program is the shell" below).

The option is in "make menuconfig" under EmuCON.  It is off by default for
the ROM images (Atari, Amiga), which keep EmuCON in the ROM; it can be turned
on there too, and EmuCON is then loaded from the boot drive as well.  It needs
the loader of the program's format (CONF_WITH_ELF_LOADER on ARM,
CONF_WITH_PRG_LOADER on m68k).  ColdFire is not supported: the standalone
build makes plain m68k code, whose Line-A calls (cmdasm.S) are not those of
ColdFire, so the ColdFire images keep EmuCON in the ROM.
On x86-64 the program is the x32 EmuCON (obj/x32/emucon.elf, see "PC (x86-64,
built-in EmuCON)" below), copied to cli/emucon.tos and run as an ordinary
ring-3 process; it goes on the EFI system partition next to EFI/BOOT, as
EMUCON.TOS.  Without the option the image embeds it.

EmuDesk as a program (CONF_EXTERNAL_DESK)
-----------------------------------------

The desktop can be a program too.  With CONF_EXTERNAL_DESK (on by default for
rpi1-rpi4, virt-arm and virt-m68k; "make menuconfig", under EmuDesk desktop)
EmuDesk is not linked into the kernel: "make" also builds emudesk.prg, and the
AES starts it with Pexec() from the root directory of the boot drive, as
EMUDESK.PRG, instead of the desktop that is in the image.  EMUDESK.INF, its
settings, is read from there as before.  The file is the objects of desk/, the
helpers of util/ that they call, and a small runtime (desk/deskrt.c) that
gives the program what the kernel's own desktop reads from the variables of
the AES, the VDI and the BIOS: the sizes of the screen and of the character
cells from the AES and the VDI (on a virtual workstation of its own), and the
rest -- the boot flags, whether the resolution can change, the caches, ... --
from Ssystem() (S_DESKINFO and S_DESKSET, bdos/ssystem.h).  Ssystem() is part
of the m68k kernel when this option is on; the other m68k images do not have
it.  The language is the LANG variable of the environment, as for EmuCON.

On ARM it is built for the Pi 1, the oldest CPU, so that the same file works
on every Raspberry Pi card.  "make test-dir", "make test-hd" and
release-raspi-resources put it on the boot drive (RASPI_EMUDESK=<file> for the
last, in the same way as RASPI_EMUCON).

On x86-64, pc-x86_64-desktop_defconfig builds EmuDesk as an ordinary x32
ring-3 ELF executable. Put emudesk.prg on the boot drive as EMUDESK.PRG,
alongside EMUCON.TOS and EFI/BOOT/BOOTX64.EFI. Its resource pointers stay in
user memory; its adapter uses typed AES snapshots/events/windows, a private
VDI workstation and bounded shell/settings calls. Raw GEM trap class 2 is
still refused from ring 3. See doc/aes-x32.txt for the service contracts and
the repeatable QEMU desktop/accessory/application integration test.

The option needs the loader of the program's format (CONF_WITH_ELF_LOADER on
ARM/x32, CONF_WITH_PRG_LOADER on m68k). It is not offered with ARM/m68k MMU
kernels (CONF_WITH_USER_ASPACE), whose processes still need a validated GEM
entry (doc/mmu-address-space.txt).

Which program is the shell
--------------------------

A kernel that has no built-in shell -- the desktop and the command line are
programs -- looks for one in the root directory of the boot drive and starts
the first of these that is there, in this order:

  with an AES      emudesk.prg, desktop.prg, emucon.tos, emucon2.tos,
                   command.tos, shell.prg, shell.tos
  without an AES   emucon.tos, emucon2.tos, command.tos, shell.tos

(the programs of the first list that only make sense with an AES are not
looked for without one).  A kernel with a built-in EmuCON but an external
desktop looks for emudesk.prg and desktop.prg only, and runs the built-in
EmuCON if neither is there.  The Console item of the desktop uses the second
list.  If nothing is found the kernel says so on the console (include/shells.h
has the lists).

rpi2                kernel7.img, for the Pi 2B
rpi3                kernel8-32.img, for the Pi 3, 3+ and CM3
rpi4                kernel7l.img, for the Pi 4 and 400

QEMU loads a kernel image directly and needs nothing else, but real
Raspberry Pi hardware does: the GPU reads its own boot firmware
(bootcode.bin, start*.elf, fixup*.dat) off the SD card before it ever gets
to loading a kernel*.img. The four kernel images above are named so the
firmware picks the right one and CPU mode for whichever board is plugged
in -- including kernel8-32.img's "-32" forcing 32-bit mode on the Pi 3, 3+
and CM3 even though those boards can also run 64-bit code -- so a single SD
card built from all four boots the whole Pi 1-4 lineup and no config.txt is
needed.

This combination -- the four kernel images, the matching boot firmware
fetched by tools/fetch-raspi-firmware.sh from a pinned, checksum-verified
commit of https://github.com/raspberrypi/firmware and redistributed under
its LICENCE.broadcom, and the same optional emucurs.rsc/emuicon.rsc, doc/
subset and readme.txt every other pTOS release archive carries (see
"release-raspi-resources" in release.mk) -- ships as two files:

    ptos-raspi-<version>.zip       the loose files, to drop onto an SD
                                    card that is already partitioned and
                                    formatted
    ptos-raspi-<version>.img.zip   a raw disk image (MBR partition table,
                                    one FAT16 partition) that dd,
                                    Raspberry Pi Imager or balenaEtcher can
                                    write directly, with no manual
                                    partitioning or formatting

tools/mkraspi-image.sh builds the .img from a directory of files with
mtools, dosfstools and sfdisk, without ever mounting or loop-attaching
anything.
The FAT16 partition is always at least 256 MiB, far more than the content
needs, so the card is immediately usable for the user's own files once
flashed -- comfortably inside FAT16's own ~2 GiB limit (doc/fat16.txt), and
the extra space costs virtually nothing in the zipped archive, since it is
unused, all-zero sectors.
readme.txt's source is doc/readme-raspi.md: tools/md2atari.py renders its
Markdown headings and **bold** spans as Atari VT52 reverse-video escapes
(see "CONOUT Escape Sequences" in doc/bios.txt), the only styling EmuCON's
TYPE command -- likely how this readme actually gets read -- can show.

desk/emudesk-raspi.inf, copied to the card as EMUDESK.INF, is the same
desktop setup EmuTOS/pTOS falls back to when no EMUDESK.INF is present at
all (see desk_inf_data1/desk_inf_data2 in desk/deskapp.c: the drive and
Trash icons, and the file-type-to-icon associations), except its first
window slot has C:\*.* as its saved path instead of being empty. Since
cnx_get() (desk/deskmain.c) opens every window slot with a non-empty path
at boot, the desktop comes up with a window already open on the card's
contents instead of a bare desktop.

Both GitHub Actions workflows produce them (see "Continuous integration"
below): build.yml keeps them as a workflow artifact of every push and pull
request, so a card to test a change on real hardware is one download away
without waiting for a release, and release.yml additionally attaches them
to every tagged release.

ARM virt
--------

virt-arm            virt-arm.elf, for QEMU's generic ARM "virt" board

The virt board is emulation only; there is no such physical machine.  It
gives the ARM port a target that does not depend on Raspberry Pi hardware
at all: a PL011 serial console, a GICv2 interrupt controller and the ARM
generic timer.  The image is an ELF file rather than a raw binary, because
RAM starts at physical 0x40000000 while EmuTOS is linked at the usual low
addresses, and QEMU's ELF loader is what places it correctly.  Run it with:

    make virt-arm_defconfig && make
    qemu-system-arm -M virt -cpu cortex-a7 -m 128 -kernel virt-arm.elf \
        -d guest_errors -serial stdio

The RAM size follows -m, read from the memory node of the device tree QEMU
passes in r2 (128 MiB is assumed without one): from 8 MiB up to 1 GiB is
used, the rest is ignored.  The RAM, which is at 0x40000000 on this
board, is mapped at virtual address 0, where the kernel is linked (its first
16 MiB are also mapped at the physical address, which a software reset needs
to switch the MMU off), and the
devices are moved out of its way: the hardware addresses from 0x08000000 up
to 0x0fffffff (the GIC, the UART, the virtio-mmio transports) are at 0xf0000000
plus that address, and the PCIe windows, which start at 0x10000000, at
0xc0000000 plus the address minus 0x10000000.

Adding "-S -s" lets a remote gdb attach, as with the Raspberry Pi
configurations.

m68k virt
---------

virt-m68k           virt-m68k.elf, for QEMU's generic m68k "virt" board

Also emulation only, and also an ELF image for the same reason (QEMU's
-kernel loader), but otherwise unrelated to the ARM virt board above: no
Atari-compatible chipset, no MMU trick needed (this board's RAM already
starts at physical 0x0, where EmuTOS expects it). Console, interrupt
routing and the periodic tick come from three "Goldfish" devices (a TTY,
a PIC, and an RTC used as a one-shot alarm re-armed on every interrupt).
Run it with:

    make virt-m68k_defconfig && make
    qemu-system-m68k -M virt -m 128 -cpu m68020 -kernel virt-m68k.elf \
        -d guest_errors -serial stdio

Both flags after -M virt matter, not just the -kernel one: -m sets the RAM
size, which the image reads from the bootinfo list QEMU puts after it (a
size of 2 GiB or more is limited to just under 2 GiB, and 128 MiB is assumed
if there is no list), and -cpu selects the CPU.  -cpu m68020 and
-cpu m68040 both work with the image as built.  -cpu m68060 needs the
kernel built with CPUFLAGS="-m68060" (menuconfig), because QEMU has no
software package for the 64-bit mulu.l/divu.l that -m68020 code
generation may use.  The boot-time CPU detection does not read the
68060-only PCR on this board, since QEMU fatally aborts the whole VM on
that read instead of raising a guest exception, and the cache and MMU
register instructions QEMU's 68060 lacks are skipped.

virt-m68k-cli_defconfig boots to EmuCON instead of the desktop, and
virt-m68k-cli-fastcall_defconfig is the same with CONF_WITH_MFASTCALL set
(it needs the -mfastcall toolchain, see above): the way to run the
regression suite under the register-argument calling convention without
an Atari emulator.

virt-m68k-fastcall_defconfig is virt-m68k_defconfig (AES/VDI/desktop)
built the same way, for running the GEM desktop and benchmarks under
-mfastcall.

virt-m68k-mmu_defconfig is the m68k MMU configuration of #549:
virt-m68k-cli-elf with CONF_REQUIRE_PMMU set.  Its first instructions
check for a 68040 or 68060 with an MMU; on any other CPU (-cpu m68000,
m68010, m68020, and QEMU's m68030, which emulates no PMMU) it prints why it
cannot run on the serial console and stops.  On -cpu m68040 it is a
higher-half kernel (#569, doc/mmu-address-space.txt): linked at 0x80000000,
with the 68040 MMU switched on from its first instructions, and it boots to
EmuCON as virt-m68k-cli does.  (On m68060 it gets past the check, with the
-m68060 caveat above, but QEMU's 68060 has no MMU registers.)
tools/test-pmmu-check.sh boots it on both kinds of CPU, and
tools/run-regression-tests.sh virt-m68k-mmu runs the regression suite on
-cpu m68040.

virt-m68k-aspace_defconfig is virt-m68k-mmu with every process in an address
space of its own (CONF_WITH_PROCESS_ASPACES, #570): EmuCON and the programs it
starts run in user mode with page tables of their own, and a fault ends only the
process.  It needs -cpu m68040 and an EmuCON built for the kernel (the build does
that: CLI_SSYSTEM, cli/Makefile).  tools/run-regression-tests.sh virt-m68k-aspace
runs the regression suite on it.  The same option on ARM (#568) is
virt-arm-aspace_defconfig (qemu-system-arm -M virt,highmem=off -cpu cortex-a7)
and rpi2-aspace_defconfig (a Raspberry Pi 2 with EmuCON on the UART;
qemu-system-arm -M raspi2b, tools/run-regression-tests.sh raspi2b-aspace).
doc/mmu-address-space.txt describes what they do.

PC (x86-64, UEFI boot)
----------------------

pc-x86_64           pc-x86_64.efi, a PE32+ EFI application
pc-x86_64-eager     the same without demand paging (CONF_WITH_DEMAND_PAGING
                    off): a process's memory is backed when it is handed
                    out, as with the 32-bit MMU backends of #549 (#562)

Unlike every other pTOS image, this is not loaded directly by an
emulator's -kernel/-bios flag: it is booted the way real UEFI firmware
boots anything, by placing it at \EFI\BOOT\BOOTX64.EFI on a FAT-formatted
EFI System Partition and letting firmware find it there. QEMU's "fat:"
driver can synthesize that filesystem from a plain directory, and OVMF
(the Debian/Ubuntu "ovmf" package) is a UEFI firmware build QEMU can use
in place of a legacy BIOS:

    make pc-x86_64_defconfig && make
    mkdir -p esp/EFI/BOOT
    cp pc-x86_64.efi esp/EFI/BOOT/BOOTX64.EFI
    cp /usr/share/OVMF/OVMF_VARS_4M.fd .
    qemu-system-x86_64 -machine pc -m 256 -cpu qemu64,+pdpe1gb \
        -drive if=pflash,format=raw,readonly=on,file=/usr/share/OVMF/OVMF_CODE_4M.fd \
        -drive if=pflash,format=raw,file=OVMF_VARS_4M.fd \
        -drive format=raw,file=fat:rw:esp \
        -serial stdio -display none

OVMF_VARS_4M.fd holds UEFI's writable NVRAM (boot order, variables), and
QEMU writes to it as the VM runs; the package's copy under /usr/share is
root-owned on a normal Debian/Ubuntu install, so it is copied to a
writable local file first rather than used in place. `-cpu qemu64,+pdpe1gb`
is required because QEMU's default `qemu64` CPU does not advertise the 1 GiB
page support needed by the x86-64 physical-memory map.

The defconfig intentionally sets `CONF_WITH_AES=n`, so this command is a
headless EmuCON boot check. The UEFI GOP framebuffer also supports the AES and
EmuDesk desktop: to test it, enable **AES -> Include the AES and the EmuDesk
desktop** in `make menuconfig`, rebuild, and use a graphical display such as
`-display gtk` instead of `-display none`.


Countries and languages
=======================

The country selects the keyboard layout, the character set and the date and
time format.  It is picked in the "Localization" menu of the configuration.

A single-country image contains only the messages of that country, which
saves a large amount of space; this is what most configurations use.  Turn
"Build a single-country image" off to get an image that supports every
country and picks one at boot time, from the NVRAM if the machine has one,
and otherwise from the country code stored in the OS header.  The atari512,
aranym, firebee and prg configurations are multi-language.

The country can also be overridden for a single build, without touching the
configuration.  This is how the release archives are built for every
country in turn:

    make atari256_defconfig
    make COUNTRY=de UNIQUE=de

COUNTRY sets the country code in the OS header, UNIQUE restricts the image
to that one country.  Leave UNIQUE empty for a multi-language image.

Continuous integration
======================

GitHub Actions builds the tree on every push and pull request to master.
The workflows live in .github/workflows:

build.yml       builds every configuration in configs/ as a job of its own,
                so a failure names the machine it broke, and builds the m68k
                release archives and the Raspberry Pi SD card image (see
                above).  Every image is kept as a workflow artifact.
release.yml     publishes a GitHub release.  It runs when a version tag such
                as v0.1.0 is pushed, and can also be started by hand, which
                publishes a snapshot prerelease instead.

Both get their toolchain from .github/actions/setup-toolchain, which is the
authoritative list of what a build needs installed.  Adding a configuration
to configs/ is enough to have it built; the matrices are derived from that
directory rather than listed in the workflows.


Kernel-private process records
==============================

CONF_WITH_KPROC keeps a record per process in kernel memory, next to its
GEMDOS basepage (bdos/kproc.c): the launching process (Pterm() uses it
instead of the basepage's p_parent), whether the process was launched, its
DTA pointer, and its standard handle map and current directories, which are
then no longer read from or written to the basepage's p_uft and p_curdir
fields (as in FreeMiNT).  It is mandatory on x86-64, where ring-3 processes
can write their whole basepage, and optional on every other architecture,
where it is off by default (a program can overwrite the kernel there
anyway).  Turn it on in "make menuconfig" to run the same code the x86-64
port runs; programs that look at p_uft or p_curdir of their own basepage
then see zeros.  The configurations rpi2-kproc and atari512-kproc build with
it on.  Everything that is specific to per-process address spaces (page
tables, kernel stacks, loaned memory, the ancestors' basepage copies) is
selected by CONF_WITH_USER_ASPACE, which only the x86-64 port sets.  It
selects CONF_WITH_PROCMEM (and CONF_WITH_KPROC): the memory blocks of a process
(basepage with TPA, environment) then come from the procmem window
(include/procmem.h) with owners, generations and pins, not from the GEMDOS
memory descriptor lists.  Neither is user-selectable; they follow the
architecture.

CONF_WITH_USER_COPY checks the pointer arguments of every GEMDOS call
(bdos/uaccess.c) before the call runs: each pointer a call really uses must
name memory the process may read, or write for an output, for the whole
length the call touches, or the call fails with EIMBA (ERANGE for a bad
length).  It is mandatory on x86-64 and optional on ARM and m68k, where
without per-process address spaces it only rejects null pointers and bad
lengths.  On m68k, whose trap frame packs the arguments in 16-bit words, the
frame is first unpacked into one value per argument, with the widths of the
call's FSHAPE_* (check_frame_args() in bdos/bdosmain.c).  The rpi2-kproc and
atari512-kproc configurations build with it, and CI runs the regression
suite (tests/gemdos_pointers) on the latter.



Native FAT file lifetimes
-------------------------

CONF_WITH_FAT_FILE_LIFETIMES controls retained native FAT file lifetimes.
It defaults off for the 192 KB ROM and on for other images. With it enabled,
deleting an open file removes its name but keeps its contents until the last
handle or backing reference closes. Interrupted deletion and FAT reclamation
are retained for retry, and pending clusters cannot be allocated again.

With it disabled, deletion uses traditional GEMDOS semantics: another
process's open file cannot be deleted; the caller's handles are closed before
its clusters are freed. If a file identity has been shared with another
process through standard-handle inheritance, deletion is conservatively
refused until all handles to that identity close (even after the child exits).
Close and reopen the file before deleting it. Directory-allocation and
media-change safety remain
enabled. CONF_WITH_FILE_PINS selects extended lifetimes automatically, so
file mappings cannot be configured without them.


Adding a configuration option
=============================

Options live in the Kconfig file of the directory they belong to
(bios/Kconfig, vdi/Kconfig, ...), or in one of the top level Kconfig.*
files for the machine, the image format and the localization.  A bool
option named CONF_WITH_FOO becomes "#define CONF_WITH_FOO 0" or
"#define CONF_WITH_FOO 1" in the generated header, so the sources can test
it with #if even though -Wundef is in effect.

Options named MACHINE_* and TARGET_* are only defined when they are set, so
that they can be tested with #ifdef, and options named BUILD_* never reach
the C code at all.

To make a source file conditional, add it to the obj-y list of the
directory it lives in with the matching option, Linux style:

    obj-$(CONF_WITH_FOO) += foo.o
