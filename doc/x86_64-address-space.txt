pTOS - x86-64 per-process address spaces
=========================================

How a ring-3 x32 process sees memory on the x86-64 port (#329, #401, #398).  The
implementation is bios/machine/pc-x86_64/aspace.c, with the interface in
include/procmem.h; process memory and the kernel heap it builds on are in
doc/x86_64-memory.txt.


Isolation
----------

Every process has its own page-table root (the PML4 of an X86_64_ASPACE).
Only the kernel half (PML4 slots 256-511) is shared, copied from the kernel's
master table; none of its entries has the user bit, so ring 3 can never
reach the kernel image or the physical direct map.  The low half starts
with only the kernel's own low data, supervisor-only (see "Kernel low
mappings" below); nothing else is visible to a process except what is
explicitly mapped for it, so the process window, in particular, is not there
except for the process's own blocks.

The handle lives in the process's kernel-private KPROC record, never in the
public basepage, and is destroyed with it (see "Lifecycle" in
doc/x86_64-memory.txt).  Its metadata comes from the growable kernel heap.

Two kinds of leaf pages are mapped:

  private    x86_64_aspace_map_private(): fresh zeroed pages owned by the
             address space and freed with it.  Because backing is per
             process, two address spaces can map the same virtual addresses
             (the program image at X86_64_USER_IMAGE_BASE, the stack) to
             different pages and neither sees the other's writes.

  window     x86_64_aspace_map_procmem(): the process's basepage, environment
             and TPA, which the BDOS reaches by the same address (see
             doc/x86_64-memory.txt).  These addresses are unique across
             processes, so they never overlap; the blocks are pinned while
             mapped.

Permissions are explicit on every mapping: ASPACE_PROT_WRITE, _EXEC (NX
otherwise) and _USER.  The effective permission of a page is the AND of every
level, exactly as the MMU computes it; x86_64_aspace_translate() reports it.


Validating user pointers
-------------------------

A user pointer is valid for a process iff every page it covers is mapped in
THAT process's page tables, user-accessible and, for a write, writable
(x86_64_aspace_user_range_ok()).  A numeric range check is not enough: an
address can be below 4 GiB and still unmapped, supervisor-only or read-only.
The check also refuses an empty range, a wrap-around and anything reaching
X86_64_USER_VA_LIMIT.

kproc_validate_user_range() / _write() make that check for the current
process, and kproc_copy_from_user() / kproc_copy_to_user() copy through the
physical direct map after it, so a validated copy cannot fault and works
whichever address space is loaded.  A process without an address space (a
kernel-code process such as the AES's ROM programs, running in ring 0) keeps
the recorded-range check.


Kernel low mappings
--------------------

Ring 0 services a process's system calls under that process's own CR3, so
the kernel's low-half data must be reachable there too.  x86_64_aspace_create()
copies the kernel's 2 MiB mappings of

    0x00000000 - 0x001fffff   the system-vector area (OS variables, vectors)
    0x00800000 - ...          the low kernel-data pool, then the framebuffer

into every address space WITHOUT the user bit.  Ring 3 faults on any of it,
the null guard included, so a process still cannot read or write the system
variables (EmuCON asks Ssystem() for _nflops, for example).  The pool and the
framebuffer sit above the 4 MiB image window so that they never overlap what a
process maps for itself; x86_64_low_kernel_range() says where they end.

Ring 0 can still write that data on a process's behalf through a pointer
argument it did not check.  The GEMDOS (trap 1) calls are covered: every
pointer a call uses is checked against the process's own mappings before the
call runs (bdos/uaccess.c; doc/x86_64-syscall.txt lists them), so the
supervisor-only system variables, which have no user bit, cannot be reached
that way.  The BIOS and XBIOS calls other than the Rwabs-family buffers still
trust their pointers (#352), and VDI/AES are refused from ring 3 (#376).


Minimum x32 user virtual layout
--------------------------------

For the built-in EmuCON image and its process data (the constants are in
include/procmem.h):

    0x00000000 - 0x001fffff   unmapped: null guard (2 MiB)
    0x00200000 - 0x003fffff   basepage, environment and TPA blocks (window)
    0x00400000 - 0x007fffff   program image: text, data, bss (4 MiB)
    0x3ffb0000 - 0x3ffb0fff   ancestors' basepages, read-only (below)
    0x3ffc0000 - 0x3fffffff   user stack (256 KiB), growing down from
                              X86_64_USER_STACK_TOP; the page below it is
                              left unmapped as a guard

The image address matches the link address of the x32 programs (the
Makefile's -Ttext-segment=0x400000).  EmuCON is about 20 KiB of code plus a
192 KiB static heap, so 4 MiB is a generous bound; larger images or an
arbitrary ELF placement policy are not part of this milestone.  The whole
layout lies below 4 GiB, as the 32-bit ABI fields require.

A built-in image (include/x32image.h: EmuCON, and the boot self-test's probe
program) is attached to the process's KPROC record with kproc_set_image().
kproc_prepare_user() then maps every PT_LOAD segment as private pages with the
segment's own permissions (text and read-only data read+execute, data and bss
read+write -- never both write and execute) and the 256 KiB private stack,
and records the entry point and initial RSP in the KPROC record: the process
is entered there, not at whatever its user-writable basepage says.  A bare
basepage's TPA is not a stack; only built-in images have one of their own.
This is not a general ELF loader (the rules are in x32image.h and checked
before anything is mapped).


Faults and termination
-----------------------

A ring-3 process leaves by Pterm() or by a fault, and in both cases control
returns to the kernel context that launched it (bdos/arch/x86_64/rwa.c):
gouser() saves a jmp_buf before iretq, and termuser() unwinds to it once
xterm() has destroyed the address space, so the launcher's Pexec() returns
the exit code.  A fault in ring 3 (bios/arch/x86_64/panic.c) is reported on
the console with the vector, error code, RIP, CR2 and RSP, and ends that
process as Pterm(-1) (exit code 0xffff); only an exception in ring 0 is fatal
to the machine.  Returning from a syscall that never reaches its exit stub
also undoes that stub's `swapgs` (x86_64_syscall_abandoned()).

Each ring-3 process makes its system calls on a kernel stack of its own (four
pages from the physical allocator, reached through the direct map; the KPROC
record owns it, x86_64_kstack_alloc() in include/procmem.h).  gouser() points
the syscall entry at the child's stack when it launches it and restores the
launcher's when the child is gone, so a process can run another from inside its
own Pexec() system call -- EmuCON running a program -- and the suspended
launcher's frames, and the jmp_buf it resumes through, survive the child's calls.
What else belongs to the launcher and is put back: its page tables (the
child's destruction leaves the kernel's loaded), the user RSP the entry stub
parked in the per-CPU area (one slot, overwritten by every call the child
makes) and its GS state (the launcher is inside a call, with the kernel GS base
swapped in; the child is entered, and exits, in the user state).  The child's
kernel stack is freed by the launcher after the exit, never by xterm(): Pterm()
is still running on it.

Pexec() from ring 3 builds the child's basepage, environment and program
under the parent's page tables, in blocks allocated after the parent's address
space exists.  Each is therefore borrowed into the parent's address space,
supervisor-only and pinned, when it is allocated (kproc_borrow(), called from
alloc_env()/alloc_tpa() for a ring-3 launcher) and returned when it is freed
(kproc_unborrow(), from the release path); no other process's block is ever
mapped, so a syscall pointer into a peer's memory faults in ring 0 instead of
reading or writing it.

Basepages in ring 3 (#416)
--------------------------

All Pexec() modes are accepted from ring 3 except the kernel-internal
PE_RELOCATE.  PE_BASEPAGE, PE_BASEPAGEFLAGS and PE_LOAD return a basepage the
caller can use: its blocks (basepage/TPA and environment) stay borrowed, but
are re-granted to the caller as user memory (kproc_hand_over()).  The caller
may rewrite the basepage, grow p_hitpa up to the end of its block, and place
code in the TPA.

A basepage handed to PE_GO or PE_GOTHENFREE is only a request.  The kernel
keeps its own record of every basepage it made (KPROC), including who made it
and whether it was launched, and kproc_check_launch() accepts the request only
if that record says this very caller made it and nothing has launched or freed
it since (block identities are checked, so a reused address does not pass).
Anything else -- a copy of a basepage, a block that is no basepage, somebody
else's, an already launched or freed one, the caller's own running basepage --
is EIMBA.  The fields the caller may have changed are then validated, each
read once: p_lowtpa must be the basepage itself, p_hitpa within its block
(rounded for the initial stack alignment), p_tbase inside the TPA, p_env the
recorded environment block; otherwise EPLFMT.  The entry point, stack and
bounds the launch uses come from the record and the validated values, never
from fields that were not checked.

A ring-3 process cannot see its launcher's basepage (it is not mapped for it),
and its p_parent could not be believed if it could.  Instead each process has a
read-only page of scrubbed copies of its ancestors' basepages at
0x3ffb0000: its launcher's, that one's launcher's, and so on, up to
16 levels, 256 bytes each, chained through p_parent (the last is 0) and
p_parent of the process itself points at the first.  The copies come from the
launcher at the time of the launch, extended by the launcher's own page.  In
each copy p_env is the *process's own* environment (so nothing dangles), and
p_uft, p_curdir, p_xdta, and the saved registers are zero.  A process can
read what its ancestors were told (command line, flags, drive), and nothing
it could use against them.  The kernel never reads p_parent: Pterm() uses the
launcher recorded in the KPROC.

File handles and directories (#418): the standard-handle map (p_uft) and the
per-drive current directories (p_curdir) are kept in the process's KPROC record,
not in its basepage, which a ring-3 process can overwrite.  The p_uft/p_curdir
fields of such a basepage are unused (zero), as in FreeMiNT; the kernel reaches
the tables only through PD_UFT()/PD_CURDIR() (include/bdosdefs.h), which are the
plain fields on every other architecture and for the boot-time basepages that
have no record.  The tables are released through the record when the process
ends or when a never-launched basepage is freed.  Probe mode t of the self-test
scribbles over both fields and must still do file, directory and console I/O.

Interrupts stay disabled in ring 3 and in system calls, as everywhere else in
this kernel (devices are polled).  The exception stack (TSS rsp0) is still
shared: an exception never resumes the code it interrupted, so nothing on it
outlives the fault.


Not covered here
-----------------

Sharing read-only image pages between processes, demand paging, copy-on-write,
Mmap/Munmap and relocation-free loading of arbitrary ELF files.

Tests: the boot-time self-test (bios/machine/pc-x86_64/memtest.c) launches the
probe program of tests/x32_probe/ in ring 3 -- entry registers, selectors and
stack alignment, a GEMDOS call across the syscall boundary, bad system call
arguments, exit codes, fresh private pages per process, three kinds of fault
-- and checks after each run that CR3, the GS bases and every allocator are
back where they were.  With C:\X32HELLO.TOS on the boot drive (CI puts it
there) the probe also runs it through Pexec() from ring 3 and must resume and
keep making calls ("x86-64 nested pexec: PASS"), and checks that a grandchild sees two ancestor
basepages ("x86-64 ancestors: PASS").  Basepage handling (mode g of the probe) builds,
launches and frees basepages and tries forged launches.  The CI boot test requires its PASS line and that the
built-in EmuCON ran afterwards without a fault.
