pTOS - ELF executable loader
============================

pTOS can load programs in two formats.  The classic Atari GEMDOS PRG format
(bdos/kpgmld.c) is m68k specific: its relocation table is a byte stream of
m68k address fixups that ARM cannot produce at all.  Alongside it sits a
second, ELF based loader (bdos/elfld.c), enabled by the CONF_WITH_ELF_LOADER
option (on by default on ARM, available on m68k as an alternative to PRG).

Pexec() chooses between the two by inspecting the file's magic number, so
both formats coexist: a file starting with 0x7f 'E' 'L' 'F' is loaded by the
ELF loader, one starting with 0x601a by the PRG loader.

An ELF binary can also import pTOS system functions as ordinary typed C
function calls, resolved when the program is loaded. The optional x32 VDI
client supplies the vdi:vdi import; see "Native pTOS ABI imports" below.


Why relocation is needed
------------------------

pTOS has no MMU and a single physical address space, so a program is loaded
wherever there happens to be free memory, not at a fixed virtual address.
The loader must therefore fix up every absolute address in the program once
it knows the real load address -- exactly what the GEMDOS relocation table
does on m68k.  The ELF loader gets the same information from standard ELF
relocation entries and applies the same additive fixup:

    *slot += actual_load_address - link_base

Only 32-bit absolute relocations need this (R_ARM_ABS32 / R_ARM_RELATIVE on
ARM, R_68K_32 / R_68K_RELATIVE on m68k, R_X86_64_32 / R_X86_64_RELATIVE on
x86-64's x32); PC-relative slots are left alone
because a uniform shift of the whole image preserves their offsets.


Accepted binaries
-----------------

(On x86-64 the image is not placed in the TPA at all: it is read, and relocated
by this loader if it was not linked for the image window, straight into the
pages the process will run from, in the process's own address space or, for a
PE_LOAD by a ring-3 caller, in a block of the caller's heap, see
doc/x86_64-address-space.txt.)

The loader accepts a statically linked, native-endian ELF32 for the machine
it was built for, in either of two forms:

  1. A fixed base ET_EXEC linked with "ld --emit-relocs" (ld -q).  Normally
     ld consumes and discards relocations at link time; -q keeps them in the
     final binary so the loader can re-apply them at a different base.

  2. A position independent ET_DYN (PIE), linked with
     "ld -pie --no-dynamic-linker".  A PIE carries only the additive
     R_*_RELATIVE dynamic relocations it actually needs, and a program that
     stores no absolute pointer in its initialised data needs none at all.

In both cases the relocation entries are read from the section headers, so
the binary must keep them: do not strip it (no "strip", no "ld -s").  A
binary that must be relocated but has no usable section header table is
rejected.  Both ELF relocation encodings are applied: REL sections
(SHT_REL), which ARM emits with the addend stored in the target word, and
RELA sections (SHT_RELA), which m68k emits with an explicit addend field.


Building a compatible program (ARM)
-----------------------------------

This works with a stock arm-none-eabi toolchain, no patched gcc or ld:

  # fixed base, --emit-relocs.  -mword-relocations keeps gcc from emitting
  # MOVW/MOVT split relocations, so every absolute slot is a plain 32-bit
  # R_ARM_ABS32 word that the loader can fix up directly.
  arm-none-eabi-gcc -ffreestanding -nostdlib -fno-pic -mword-relocations \
      -c prog.c -o prog.o
  arm-none-eabi-ld -q -Ttext=0 -e _start prog.o -o prog.elf

  # or, position independent:
  arm-none-eabi-gcc -ffreestanding -nostdlib -fPIE -c prog.c -o prog.o
  arm-none-eabi-ld -pie --no-dynamic-linker -e _start prog.o -o prog.elf

The result is an ordinary ELF that readelf, objdump and gdb understand.
"readelf -r prog.elf" shows the relocations the loader will apply.


Building a compatible program (m68k)
------------------------------------

The same two recipes work with m68k ELF toolchains.  Besides a bare-metal
m68k-elf- toolchain, Vincent Riviere's mintelf toolchain
(m68k-atari-mintelf-) can produce ELF executables for the loader as well.
The m68k psABI uses RELA relocations, so the retained entries are
R_68K_32 / R_68K_RELATIVE in SHT_RELA sections; the loader handles those:

  # mintelf toolchain (ELF output).  m68k-atari-mintelf-ld defaults to
  # elf32-atariprg, so force a generic ELF32 target explicitly:
  m68k-atari-mintelf-gcc -ffreestanding -nostdlib -fno-pic -c prog.c -o prog.o
  m68k-atari-mintelf-ld --oformat=elf32-m68k -q -Ttext=0 -e _start \
      prog.o -o prog.elf

  # or, position independent:
  m68k-atari-mintelf-gcc -ffreestanding -nostdlib -fPIE -c prog.c -o prog.o
  m68k-atari-mintelf-ld --oformat=elf32-m68k -pie --no-dynamic-linker \
      -e _start prog.o -o prog.elf

  # bare-metal toolchain equivalents:

  # fixed base, --emit-relocs:
  m68k-elf-gcc -ffreestanding -nostdlib -fno-pic -c prog.c -o prog.o
  m68k-elf-ld -q -Ttext=0 -e _start prog.o -o prog.elf

  # or, position independent:
  m68k-elf-gcc -ffreestanding -nostdlib -fPIE -c prog.c -o prog.o
  m68k-elf-ld -pie --no-dynamic-linker -e _start prog.o -o prog.elf

Programs start executing at the ELF entry point (e_entry); the PT_LOAD
segments are placed in the TPA and the rest of it, including .bss, is zeroed.


Compact load relocations (.ptos.reloc / PT_PTOS_RELOC)
-------------------------------------------------------

The two forms above both make the loader depend on the ELF section header
table: the retained SHT_REL/SHT_RELA sections from "ld --emit-relocs" carry
far more than a load-time fixup needs (symbol/section tables meant only for
linking, entries for sections that are never loaded, ...), and the binary
can never be stripped of its section headers.

pTOS also accepts a third, preferred form: a post-link tool (tools/
ptos-elf-pack.c) reads either of the two forms above and rewrites it into an
architecture-neutral, compact relocation stream, addressed through a
pTOS-private program header instead of the section header table. This is
the first piece of the larger native pTOS ABI work tracked by issue #308;
this document covers only the relocation format, which stands on its own.

Nothing already in the file moves or resizes -- the rewrite is two additions
appended after the original content:

  1. the ".ptos.reloc" payload: an 8 byte header followed by a ULEB128
     delta stream (below);
  2. a new program header table (a copy of the original entries plus one
     new PT_PTOS_RELOC entry), which the rewritten ELF header now points at
     via e_phoff/e_phnum.

A RELA-encoded RELATIVE slot's own bytes are the one exception: as covered
below, ptos-elf-pack overwrites that existing slot with its addend in
place, so the file is not byte-identical to the input in that case -- only
unmoved and unresized. An unmodified ELF header, program headers and
section headers stay individually valid regardless; only e_phoff and
e_phnum change, to point at the new table.

PT_PTOS_RELOC's value is 0x60000001, inside the OS-specific range the ELF
spec reserves (PT_LOOS..PT_HIOS, 0x60000000..0x6fffffff). Its p_offset/
p_filesz locate the ".ptos.reloc" payload; p_vaddr/p_paddr/p_memsz are 0
(the segment is metadata, not something to map into the process image).

".ptos.reloc" payload layout, version 1:

    offset  size  field
    0       4     magic   (0x50544c31, native byte order, checked exactly)
    4       2     version (1)
    6       2     reserved (0; ignored by version 1 readers)
    8       -     ULEB128 stream, one value per relocated slot

Each ULEB128 value is a *delta*: the first is the distance from the image's
link_base (the lowest p_vaddr of any PT_LOAD segment, as elsewhere in this
document) to the first relocated slot; every value after that is the
distance from the previous slot to the next one. Slots are therefore
listed in strictly ascending address order, exactly like the classic PRG
relocation table's fixup stream. The stream ends when it has consumed
p_filesz - 8 bytes; there is no explicit terminator.

Version 1 has exactly one relocation operation, applied to every slot the
stream lists: a native ULONG at that address gets the program's load bias
added to it --

    *slot += actual_load_address - link_base

identical to the DIR32 fixup described above. This covers everything the
current loader relocates: for input relocations that already store the
value to fix up directly in the slot (R_ARM_ABS32 / R_68K_32 / R_X86_64_32,
and ARM's REL-encoded R_ARM_RELATIVE), ptos-elf-pack lists the slot as-is; for
a RELA-encoded RELATIVE relocation (R_68K_RELATIVE on m68k, R_X86_64_RELATIVE
on x32), whose slot may legitimately be 0 in the file with the real value
carried in r_addend instead, ptos-elf-pack first writes that addend into the
slot's file bytes so every listed slot ends up needing the same "add the bias"
operation.
The optional x32 VDI imports are packaged separately from these relocation
slots. Import consumers use PIE code and the dynamic GOT/PLT relocation
metadata, without retained static PC-relative relocations against undefined
symbols; see the application recipe in doc/vdi-x32.txt.
Relocation types the loader does not otherwise apply (PC-relative and
similar) are never listed and need no entry -- but only when ptos-elf-pack
recognises the type as one of the ones known not to need a load-time fixup;
an input relocation of any other, unrecognised type is a packaging error,
not silently skipped, since guessing wrong would silently corrupt the
image.

When bdos/elfld.c finds a PT_PTOS_RELOC program header, it always uses this
stream and never touches the section header table, whether or not one is
present -- so a file built this way does not *need* its section headers,
.symtab or the original relocation sections to load correctly, even though
ptos-elf-pack does not yet actually remove any of those bytes (reclaiming
that space is a later refinement, tracked under issue #308). ptos-elf-pack's
`--strip-shdr` flag clears only the four header fields that point at the
section header table -- e_shoff/e_shnum/e_shentsize/e_shstrndx -- to prove
that a given binary has no live reference back to it; a file packed without
that flag simply carries section headers nothing then reads. Only a file
with no PT_PTOS_RELOC header at all falls back to the section-based
relocation described above, so existing unpacked ELF binaries keep working
unchanged.

Producing a packed binary is one extra step after the existing recipes
above:

    arm-none-eabi-ld -q -Ttext=0 -e _start prog.o -o prog.elf
    ptos-elf-pack prog.elf prog-packed.elf

"readelf -l prog-packed.elf" shows the extra program header as an unknown
OS-specific type (0x60000001); this is expected and harmless for any tool
that does not know about it.

ptos-elf-pack refuses to pack a fixed-base ET_EXEC with zero relocated
slots by default: that shape is indistinguishable, from the packed file
alone, from one linked without "-q"/"--emit-relocs" in the first place --
a mistake that would otherwise pack silently into a binary that corrupts
itself the moment it loads anywhere but its link address. Pass
`--allow-no-relocations` once you have confirmed the input genuinely
needs no load-time fixups (a position-independent ET_DYN is exempt from
this check, since it can legitimately need none).

Native pTOS ABI imports (.ptos.imports / .ptos.bind / PT_PTOS_IMPORTS)
------------------------------------------------------------------------

Alongside .ptos.reloc, an ELF binary may carry a second, independent piece
of pTOS-private metadata: a table of pTOS system functions the program
imports and calls as ordinary typed C functions, resolved to their ABI
addresses when the program is loaded, without a filesystem-based
dynamic linker or any runtime symbol lookup. This is the second piece of
the native pTOS ABI work tracked by issue #308 (the first being
.ptos.reloc, above); it would let a native ELF application call a pTOS
function directly, compiled and linked as a normal extern function call.

CONF_WITH_X32_VDI registers vdi:vdi, ABI 1.0, for native x32 applications.
It also selects CONF_WITH_PTOS_ABI_IMPORTS. The resolved address names the
checked client running in ring 3, mapped as private read-only executable
pages in the process (doc/vdi-x32.txt). It never names an LP64 kernel
function. Static client linking is also available. The ordinary EmuCON-only
configuration leaves VDI disabled and refuses applications requiring it.

CONF_WITH_X32_AES adds the aes: typed client functions and caller-local
helpers, also ABI 1.0 (doc/aes-x32.txt). Its image is separate from the VDI
image and its service state stays kernel-owned. No other namespace is
registered. The earlier gemdos imports were removed
because the classic trap1()/TRAP #1 interface already serves GEMDOS. ARM and
m68k retain their existing trap interfaces; enabling imports there does not
make the x32 VDI implementation available.

The ".ptos.imports" payload
............................

PT_PTOS_IMPORTS's value is 0x60000002, in the same PT_LOOS..PT_HIOS range
as PT_PTOS_RELOC. Its p_offset/p_filesz locate the ".ptos.imports"
payload; p_vaddr/p_paddr/p_memsz are 0, exactly like PT_PTOS_RELOC -- this
is metadata, not something to map into the process image. A binary that
imports nothing has no PT_PTOS_IMPORTS header at all: unlike .ptos.reloc,
there is no reason to ever emit an empty one.

".ptos.imports" payload layout, version 1:

    offset  size  field
    0       4     magic          (0x50544c32, native byte order)
    4       2     version        (1)
    6       2     reserved       (0; ignored by version 1 readers)
    8       4     import_count
    12      4     bind_count
    16      4     import_table_off  (relative to payload start)
    20      4     bind_table_off    (relative to payload start)
    24      4     strtab_off        (relative to payload start)
    28      4     strtab_size

followed by three regions, located by the offsets above rather than
assumed adjacent (each is independently bounds-checked against p_filesz):

  * the import table: import_count fixed-size 12 byte records --

        offset  size  field
        0       4     name_off   (offset into the string table below)
        4       2     abi_major
        6       2     abi_minor  (minimum required feature version; 0 = any)
        8       1     kind       (0 = function, 1 = data)
        9       3     reserved   (0)

    name_off points at a NUL-terminated "namespace:name" string in the
    string table, e.g. "vdi:v_opnwk". abi_major must match the export
    table's version for that namespace exactly (see bdos/elfld.c);
    abi_minor is a minimum the export table's own minor version must meet
    or exceed.

  * the bind table: bind_count fixed-size 12 byte records --

        offset  size  field
        0       4     import_index  (index into the import table above)
        4       4     slot_vaddr    (vaddr of the 4-byte slot to fill)
        8       1     bind_op       (see below)
        9       3     reserved      (0)

    Several bind records may name the same import_index: this is exactly
    how more than one call site or GOT slot can share one imported
    symbol without repeating its name.

  * the string table: strtab_size bytes of NUL-terminated strings,
    referenced by name_off above.

bind_op is one of:

    PTOS_BIND_CODE_ADDRESS   0   slot_vaddr <- imported function's address
    PTOS_BIND_DATA_ADDRESS   1   slot_vaddr <- imported data symbol's address
    PTOS_BIND_GOT_SLOT       2   slot_vaddr <- imported symbol's address

All three write the plain resolved address into the 4-byte slot and are
functionally identical in version 1; they are kept distinct because a
later FDPIC-aware version (issue #308) will need to write a two-word
function descriptor instead of a bare code address for a function import,
and needs to tell that case apart from a plain data address or an
already-shared GOT slot without changing the format again. An unrecognised
bind_op is a packaging/loading error, not silently ignored, following the
same "never guess" rule .ptos.reloc's unrecognised relocation types
follow.

Every bind's slot_vaddr must satisfy the same bounds and alignment rules
as a .ptos.reloc slot (fully inside the loaded image, naturally aligned
for the target). The bind table itself must be sorted strictly ascending
by slot_vaddr -- exactly like .ptos.reloc's own delta-encoded slot stream
-- so no two binds may target the same slot_vaddr and an out-of-order
entry is equally a format error. ptos-elf-pack sorts and rejects
duplicates at pack time; the loader enforces the same invariant with a
single comparison against the previous entry as it reads the table once,
rather than re-reading every earlier bind for each new one.

How ptos-elf-pack builds it
............................

ptos-elf-pack looks for a DT_NEEDED entry in the input's .dynamic section.
If there is none, no ".ptos.imports" payload is produced at all -- a
binary using only internal relocations is unaffected. The recognized native
stubs are libptos-vdi.so.1 and libptos-aes.so.1, each permitted once; an
application may depend on both. Known symbol names select their namespace:
vdi() belongs to vdi:, and the functions listed in aes_client_exports.h
belong to aes:. Every .rel.plt/.rela.plt or .rel.dyn/.rela.dyn relocation
against one of these undefined dynamic symbols is converted into one import
(abi_major 1, abi_minor 0, function kind) and one bind record (bind_op
PTOS_BIND_CODE_ADDRESS for R_*_JUMP_SLOT or a GLOB_DAT against a STT_FUNC
symbol, PTOS_BIND_DATA_ADDRESS for a GLOB_DAT against a STT_OBJECT symbol)
at that relocation's r_offset -- already a load-time vaddr, since
.got.plt/.got are SHF_ALLOC sections. A JUMP_SLOT is PLT machinery and
therefore only ever a function call, so one against a symbol whose type
is not STT_FUNC is a packaging error: pTOS ABI imports have no way to
represent that combination, and bdos/elfld.c's ptos_bind_apply() would
reject it as a bind_op/kind mismatch regardless.

On m68k specifically, a plain DIR32
relocation (R_68K_32) against one of those same undefined dynamic symbols
is ALSO converted the same way: this toolchain has no -fPIC/-fPIE code
generation, so a call to an imported function compiles to a plain
absolute reference (an ordinary R_68K_32 relocation on the call's own
address operand) rather than a PLT-relative one -- confirmed directly
against this toolchain's actual "-pie --no-dynamic-linker" output, which
emits exactly this shape alongside an R_68K_JMP_SLOT PLT entry the
generated code never actually references. ARM's PIC-capable codegen does
not produce this shape (only JUMP_SLOT/GLOB_DAT), so the same check
(present on both architectures) simply never matches there. Either way,
a DIR32 import carries no addend of its own -- a nonzero one, RELA-
explicit or REL-implicit, is rejected outright, since version 1's bind
mechanism has no addend component. Two bind records against the same
imported symbol are merged into references to one shared import entry
rather than duplicated. A DT_NEEDED entry that does not match this
pattern is a packaging error: pTOS has no general purpose dynamic linker,
so a real shared library dependency can never be satisfied at load time.
A relocation against an undefined dynamic symbol that is NOT covered by a
recognised libptos-abi.so.<N> dependency, or whose type is none of
JUMP_SLOT, GLOB_DAT, or DIR32, is also a packaging error rather than
something silently left unresolved -- except the architecture-defined
no-op/meaningless-symbol types (R_ARM_NONE, R_68K_NONE, R_ARM_V4BX),
which the packer's no-fixup allowlist above already accepts regardless
of what their (per the ABI, unused) symbol field names.

Only the named x32 VDI and AES client functions are accepted for packaging.
Unknown functions, data symbols and duplicate dependencies are rejected
before producing output. The
legacy libptos-abi.so.<N> stub is still recognised while parsing relocation
metadata, but its gemdos namespace remains unavailable and cannot be packed.
There is no general purpose dynamic linker and no filesystem DSO loading.

Use position-independent x32 code and link with -pie --no-dynamic-linker,
without --emit-relocs: the dynamic relocations describe the GOT/PLT imports.
Retained static PC-relative relocations against an undefined PLT symbol
remain outside the packer's accepted shapes. See doc/vdi-x32.txt for the
complete build recipe and tested fixtures.

Locating the metadata and loader resolution
............................................

bdos/elfld.c looks for PT_PTOS_IMPORTS the same way it looks for
PT_PTOS_RELOC: by walking the program header table, never the section
header table. When present, and the kernel was built with
CONF_WITH_PTOS_ABI_IMPORTS, every import would be looked up by exact
"namespace:name" match against the kernel's own registered export tables
(bdos/elfld.c's ptosabi_resolve()), with the ABI major version required to
match exactly and the minor version required to be at least the import's
requested minimum. An import naming an unknown symbol, an unsupported
namespace, or an ABI version the export table cannot satisfy fails the
whole Pexec() with EPLFMT rather than binding a null or garbage address
-- a native application must never silently call through an unresolved
slot. The x32 VDI function is available only with CONF_WITH_X32_VDI. A
PT_PTOS_IMPORTS header in a kernel built without CONF_WITH_PTOS_ABI_IMPORTS
fails to load the same way: there is no export table to resolve against,
so pretending the binary loaded correctly would leave every import slot
at 0.

Imports are resolved after .ptos.reloc/section based relocations are
applied, but the two mechanisms never touch the same slot: a JUMP_SLOT/
GLOB_DAT relocation against an undefined dynamic symbol is never one of
the relocation types .ptos.reloc lists (R_*_ABS32/R_*_RELATIVE, always
against a symbol that resolves to real image content), so ptos-elf-pack
always routes a given slot to exactly one of the two payloads, never both.

Known .ptos.reloc version 1 limitations
-----------------------------------------

A RELA-encoded RELATIVE relocation whose target lies in a PT_LOAD
segment's zero-filled tail (i.e. in .bss, past its file-backed part) is
rejected rather than packed, but only when its addend is nonzero. A zero
addend needs no rejection: the loader's own zero-fill already leaves 0 at
that address, exactly what "0 += bias" (this format's one operation)
needs there, so ptos-elf-pack packs it as-is with no write at all. Every
other slot version 1 lists -- including a nonzero-addend RELATIVE with
file backing -- is represented by baking its resolved value into the
slot's own file bytes (see the RELA-addend-materialisation note above)
and applying the same "add the load bias" operation uniformly; a
.bss-resident slot has no file bytes to bake a nonzero value into.
Representing that case correctly needs a second wire operation that
carries its own addend explicitly, which the classic loader's own
elf_fixup() already computes at runtime (bias + addend) but version 1 of
this format has no encoding for. This is a real format boundary, not a
bug: extending the format to cover it is left for a future version rather
than done ad hoc.


Known .ptos.imports version 1 limitations
--------------------------------------------

ptos-elf-pack recognises the two native client DT_NEEDED libraries,
libptos-vdi.so.1 and libptos-aes.so.1, once each. Their symbol sets are
explicit and disjoint, so no filesystem symbol search or dependency-order
resolution occurs. Further namespaces need another explicit library/symbol
mapping; this does not require a wire-format change.

abi_minor exists in the wire format (and in every export table lookup)
for exactly this reason: a future export table can grow feature-level
granularity within one ABI major version without changing the format.

Binding is purely eager and address-based: PTOS_BIND_CODE_ADDRESS writes
a bare code address, which is correct for pTOS's current non-FDPIC ABI
where every image shares one uniform load bias and one GOT/data context.
A future FDPIC-aware version, where code and data can be placed
independently (issue #308), will need a function descriptor (code address
plus the exporting image's own data context) instead of a bare address
for at least some function imports; this version has no encoding for
that, by design -- see PT_PTOS_RELOC's own single-region assumption
above, which has the identical boundary.

A future namespace's own export table should give real thought to the
same three properties that led to GEMDOS's own removal from this
mechanism (see "Native pTOS ABI imports" above): whether its handlers
can run correctly at the CPU privilege level a native ABI importer
actually executes at (bdos/proc.c's proc_go() starts every launched
process in genuine user mode), whether they depend on an ambient
setjmp/hard-error recovery frame their normal call path provides but a
direct native call would not, and whether they depend on any other
per-call context (I/O redirection and the like) an indirect trap-based
call would set up but a direct one would not.
